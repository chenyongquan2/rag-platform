# P2 报告：增量更新、索引切换、消融实验

这份报告随 P2 的子需求逐节增加。现在只有 P2-02 一节；P2-01（索引切换）和后面的子需求做完以后，各自加一节。

## 1. P2-02 阈值和读取耗时

日期：2026-10-19，分支 `spec/P2-02-thresholds`。原始记录在 git 忽略的 `data/reports/p2-02/`（每个题集一个分数文件、完整的扫描表、读取耗时记录）。

### 1.1 这一节回答什么

1. 重排分的阈值定多少合适：定得越高，没有答案的题越容易被拒绝，但有答案的题也越容易被误拒。两边各是多少，用哪条规则选。
2. 现在的默认值 0.3（P0-13 在 65 道公开题和 10 道无答案题上定的）在开发集和更多无答案题上还成不成立。
3. 把 2,647 篇文档全部读一遍、清洗一遍要多久，要不要加「没改过的文件不再读」（文件级跳过）。

先说样本量，因为它决定了哪些差别能下结论（设计 14.4）：
- 开发集 99 题：对同一批题比较两个阈值时，至少要 6 题变化、且全部朝同一个方向，才算可靠（精确 McNemar 检验，p 不大于 0.05）。
- 无答案题只有 30 道（原来 10 道，这次加了 20 道）：同样要 6 题全朝一个方向。所以两个阈值之间只差三四道题的差别，在这个题集上看不出来。
- 公开 65 题只作外部对照，不用来选阈值（设计 14.2）。

### 1.2 先说几个词

| 词 | 意思 |
|---|---|
| 重排分 | 重排模型（bge-reranker-base）给「问题和一个块」打的 0 到 1 的相关分。 |
| 阈值 | 一道题的所有候选块的重排分都低于它时，检索返回「没找到」。分数等于阈值算通过。 |
| 最高分 | 一道题的候选块里重排分最高的那个。一道题在某个阈值下是否被拒绝，只看它的最高分。 |
| 误拒率 | 有答案的题里，被拒绝的比例。越低越好。 |
| 错放过率 | 没有答案的题里，没被拒绝的比例（检索照常把块交给回答步骤）。越低越好。 |
| 正确页面丢失 | 一道题的正确页面有块进了重排，但这些块的分数全部低于阈值，页面到不了回答步骤。 |
| 话题无关的无答案题 | 问的事和 Hugging Face（HF）文档完全无关，例如「澳大利亚首都是哪里」。 |
| 话题相近的无答案题 | 问的是 HF 的东西，但文档里没有答案，例如「Hugging Face 的 Series D 融资了多少钱」（文档里只有 Series C 的文章）。 |
| Wilson 区间 | 题少时观察到的比例不准，这个区间给出真实比例大概在哪个范围（95% 把握）。 |
| 配对比较 | 同一批题在两个阈值下各算一遍，只看「从放过变成拒绝」和「从拒绝变成放过」的题，用精确 McNemar 检验判断差别是不是碰巧。 |

### 1.3 做法和用的题集

脚本是 `python -m rag.eval.threshold`，分两步：
1. `collect`：把一个题集的每道题送进真实的检索链（和 search_docs 用的同一条），阈值强制设成 0，把每个进了重排的候选块的分数存下来。这一步不调对话模型；问题向量先查本地缓存。
2. `sweep`：读这些分数文件，对每个候选阈值算误拒率、错放过率和 Wilson 区间。只有开发集参与选阈值，其余题集只报告。`--baseline` 再列出相对某个阈值有哪些题变了。

题集：

| 题集 | 题数 | 用途 |
|---|---|---|
| 合成开发集（P1-05） | 99 | 选阈值，看误拒率 |
| 公开 65 题 | 65 | 外部对照，只看误拒率 |
| 无答案题，原来的 | 10 | 看错放过率（5 道话题无关，5 道话题相近） |
| 无答案题，这次新加的 | 20 | 看错放过率（12 道话题相近，8 道话题无关） |
| 合成保留集 | 100 | 阈值定下来以后只算一次，报最终数字 |

新加的 20 道题在 `evals/datasets/hf_docs/no_answer_extra.jsonl`，是我（Claude）手写的，没有请主人审过。写之前对 2,647 篇文档做了关键词检索，确认题里问的具体事实（例如「Singapore」「recovery code」「SQuAD 3.0」「Teradata」）文档里没有，检查结果记在每道题的 `meta.checked_absent` 里。话题相近的题是照着「文档里有相关话题、没有这个答案」的样子写的，所以它们不是随机抽样，错放过率偏向难的一边。这 20 道题的向量花了 0.00014 元。

### 1.5 三条选择规则，三个答案

规则里只用开发集的误拒率；无答案题和公开题只用来看「这个阈值换来了什么」。

| 规则 | 选出的阈值 | 依据 |
|---|---|---|
| 开发集误拒率（观察到的）不超过 5% | 0.85 | 4/99 = 4.0%；0.90 是 7/99 = 7.1%，超了 |
| 开发集误拒率不超过 2%（设计 10.2 的起点） | 0.70 | 1/99 = 1.0%；0.75 是 2/99 = 2.02%，刚超 |
| 开发集误拒率的 Wilson 上限不超过 5% | 0.40 | 0/99，上限 3.7%；0.45 有 1 题，上限 5.5% |

同一批数据，三条规则选出 0.40、0.70、0.85。原因是开发集的误拒在 0.40 到 0.90 之间一道一道出现，99 题分不清「0.40 没有误拒」和「0.85 有 4 个误拒」：配对比较 0.40 对 0.85，4 题变化、0 题反向，p = 0.125，没有可靠差别。这就是设计 14.4 说的「差别小于能分辨的大小，写没有可靠差别」。

### 1.6 阈值换来了什么：看无答案题的类型

把 30 道无答案题按类型分开（话题无关 13 道，话题相近 17 道），每个阈值下没被拒绝的题数：

| 阈值 | 话题无关（共 13） | 话题相近（共 17） |
|---|---|---|
| 0.30 | 1（「澳大利亚首都」，最高分 0.493） | 13（53% 到 90%） |
| 0.40 | 1 | 12 |
| 0.50 到 0.70 | 0（Wilson 区间 0 到 23%） | 9（31% 到 74%） |
| 0.85 | 0 | 7（22% 到 64%） |
| 0.90 | 0 | 4（9.6% 到 47%） |
| 0.95 | 0 | 2（3.3% 到 34%） |

- 话题无关的题，阈值 0.5 就全部拒绝了（最高的一题 0.493）。0.3 到 0.5 之间多拒绝的 5 道题里，1 道是话题无关，4 道是话题相近。
- 话题相近的题，最高分里有 7 道在 0.85 以上（最高 0.999：问「DistilBERT 在 SQuAD 3.0 上的得分」，文档里有 SQuAD 的相关段落）。要拒掉它们，阈值要到 0.9 以上，而这时开发集误拒已经是 7/99。这类题靠阈值拒不掉，要靠回答这一步判断「片段里没有答案」（`found=false`，P1-02）。这一步对这 17 道题的效果这次没有量，量它要调对话模型。

### 1.7 配对比较：相对 0.3 变了哪些题

每格是「变成拒绝的题数 / 变成放过的题数（p）」，只摘部分阈值；全表在 `data/reports/p2-02/sweep.md`。

| 阈值 | 开发集（有答案） | 公开 65 题（有答案） | 30 道无答案题 |
|---|---|---|---|
| 0.40 | 0 / 0（p 1.0） | 0 / 0 | 1 / 0（p 1.0） |
| 0.50 | 1 / 0（p 1.0） | 0 / 0 | 5 / 0（p 0.062） |
| 0.70 | 1 / 0（p 1.0） | 0 / 0 | 5 / 0（p 0.062） |
| 0.75 | 2 / 0（p 0.5） | 0 / 0 | 6 / 0（p 0.031） |
| 0.85 | 4 / 0（p 0.125） | 0 / 0 | 7 / 0（p 0.016） |
| 0.90 | 7 / 0（p 0.016） | 1 / 0 | 10 / 0（p 0.002） |

对有答案的题，「变成拒绝」是坏事；对无答案的题，是好事。读法：
- 0.3 到 0.7：无答案题多拒绝 5 道（p = 0.062，差一点不可靠），开发集多误拒 1 道（不可靠）。
- 0.75 以上：无答案题多拒绝的题数可靠（p 不大于 0.031），开发集的误拒也在变多（0.85 时 4 题，p = 0.125 还不算可靠，0.90 时 7 题，p = 0.016 可靠）。
- 公开 65 题在 0.85 以下一道都没有误拒，到 0.90 才有 1 道。公开题和开发集不一致：开发集有四道题的最高分在 0.85 以下（0.40、0.71、0.79、0.845），而公开题里最高分最低的一题是 0.883（P0-13）。

### 1.8 结论：默认值保持 0.3

不改，原因：
1. 0.3 到 0.7 之间，没有任何一个阈值能可靠地多拒绝无答案题：最好的情形（0.5 到 0.7）是无答案题多拒 5 道，p = 0.062。
2. 能可靠地多拒绝无答案题的阈值（0.75 以上），代价是开发集误拒 2 到 4 道（2% 到 4%，设计 10.2 的起点是不超过 2%），页面丢失 3 到 5 道，每题留给回答的块从 5.6 个降到 3.7 到 4.2 个。0.3 在开发集、公开题上的误拒都是 0。
3. 按「误拒不超过 5%」的规则选出的 0.85，紧挨着可靠变差的 0.90（开发集 p = 0.016），换一批题就可能越过去。
4. 误拒和错放过的后果不对称：误拒在检索这一步就丢了答案，回答步骤救不回来；错放过还有回答步骤的 `found=false` 可以拒绝。

这是我的判断，不是数据自己说出来的。如果主人更看重少放过无答案题，规则选出的数字是 0.85，代价见上面第 2 条。要改的话，改 `kb/public/hf_docs.yaml` 的 `retrieval.threshold`。

下次什么时候重看：
- 0.5 是最先要重看的值：在开发集和公开题上的代价是 1 道、0 道，无答案题多拒 5 道。如果这个比例（30 道里 5 道）保持不变，约 40 道无答案题、其中 6 道变化时 p 就小于 0.05，也就是再补 10 到 15 道话题相近的无答案题就能分辨。
- 量一次回答步骤对话题相近无答案题的拒答率（约 17 道题，调对话模型，估计不到 0.1 元）。如果回答步骤能拒绝其中大部分，话题相近的题就不必靠阈值拒绝，阈值可以一直留在保守的 0.3。
- 换重排模型或换推理后端以后（设计 10.2、P7），先确认分数换算相同，再用这个脚本重新定。

### 1.9 保留集（只算一次）

阈值保持 0.3 是在看保留集之前定的。保留集 100 题，阈值 0.3：

| 指标 | 数字 |
|---|---|
| 误拒 | 1/100（0.2% 到 5.4%） |
| 正确页面丢失 | 1/90（0.2% 到 6.0%）（10 题的正确页面没进重排候选） |
| 平均留下的块 | 5.5 个 |

和开发集（0/99）没有可靠差别：差 1 题，p = 1.0。

### 1.10 全量读取和清洗要多久

脚本 `scripts/p2_02/read_timing.py` 做的是摄取任务在和文档库比较之前做的事：列出页面、读取、清洗。不算向量，不连 Elasticsearch。重复 3 遍，每遍新建一套清洗规则。另外量了切块，因为它也只用 CPU。

| 步骤 | 第 1 遍 | 第 2 遍 | 第 3 遍 |
|---|---|---|---|
| 列出 2,647 页 | 4.8 秒（第一次读 parquet 文件） | 0.2 秒 | 0.2 秒 |
| 读取 | 0.13 秒 | 0.12 秒 | 0.12 秒 |
| 清洗（保留 2,617 页） | 32.3 秒 | 32.2 秒 | 32.0 秒 |
| 读取和清洗合计 | 32.4 秒 | 32.3 秒 | 32.2 秒 |
| 切块（26,372 块） | 126.5 秒 | 126.3 秒 | 123.0 秒 |

结论：读取和清洗约 33 秒，远低于设计 19 章说的「10 分钟左右」，现在不加文件级跳过。几点说明：
- 读取只要 0.12 秒，因为 Hugging Face 的数据集是一个 parquet 文件（一种按列存数据的文件格式），页面文本整体在内存里，这一步没有逐个打开文件。以后接逐个文件读取的数据源（P4 的 MT5 手册、公司文档），要重新量；到时读取可能比清洗慢。
- 时间花在清洗上，平均每页 12 毫秒。同样的清洗速度下，页数要涨到约 5 万页（现在的 19 倍）才会到 10 分钟。
- 读取、清洗加切块一共约 2.6 分钟。P0-12 全量摄取总共 41 分钟，绝大部分是在等网关返回向量，所以全量重建的耗时主要看向量，不看读取。
- 量的时候别的进程占着约 28% 到 47% 的 CPU（另一个子需求在同一台机器上开发），三遍结果相差不到 1 秒，说明这个数字比较稳。

### 1.11 没解决的问题

- 无答案题仍只有 30 道，新加的 20 道是我手写的，没有请主人审；话题相近的题是照「难」的样子写的，错放过率偏高，不代表真实用户的问法分布。
- 开发集里的合成题来自 P1-05 的出题方式，分数偏低的几道题（最高分 0.40、0.71）可能有标注或出题问题，没有逐题查。
- 回答步骤对话题相近无答案题的拒答率没有量（要调对话模型）。
- 读取耗时只在 HF 这一个数据源上量过。
