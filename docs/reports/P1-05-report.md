# P1-05 报告：合成题、三项打分过滤、开发集和保留集

日期：2026-10-18。分支 `spec/P1-05-synthetic-qa`。原始记录在 git 忽略的 `data/reports/synthetic/20261018T135147Z_hf_docs_synthetic/`（段落、出题、打分、过滤明细）和 `data/reports/p1-05/`（检索评测），这里只放汇总数字。

## 1. 这份报告回答什么

1. 为什么要合成题，做出来的两套题在哪里。
2. 花了多少钱：事先估了多少，试跑以后怎么推算，实际花了多少。
3. 每一步剩下多少题，被去掉的题是因为什么。
4. 留下的题长什么样（5 道例子）。

7. 局限和下一步。

## 2. 先说几个词

| 词 | 意思 |
|---|---|
| 合成题 | 让模型读一段文档原文，按这段写出一道题和答案。 |
| 段落（span） | 从一页清洗后的原文里随机截下的一段，约 2,000 个字符。出题模型只看这一段。 |
| 三项打分 | 另一个模型给每道题打三个 1 到 5 分：能不能从这段原文答出来（groundedness）、对 Hugging Face 开发者有没有用（relevance）、不看原文能不能看懂（standalone）。提示词照 HF cookbook 的 rag_evaluation 一文。 |
| 照抄检查 | 数问题里最长有几个词连着和原文段落一模一样（大小写和标点不算）。超过 6 个词就当作照抄，去掉。 |
| 开发集 | 平时调检索参数时看的题。 |
| 保留集 | 调参时不看，每个阶段结束时报一次的题，用来确认调参没有只对开发集有效。 |
| 层 | 「源仓库加文档类型」，比如 `huggingface/transformers` 的 markdown 页是一层。抽段和拆分都按层按比例分。 |
| 关键词检索（BM25） | ES 按词匹配打分的那一路检索。 |
| 向量检索 | 把问题变成向量、找最接近的块的那一路检索。 |
| Hit@k | 前 k 条结果里有没有题目标注的那一页，有记 1，没有记 0，再取平均。 |
| MRR（Mean Reciprocal Rank，平均倒数排名） | 正确页面排第 1 记 1，排第 2 记 1/2，以此类推，取平均。 |
| nDCG@8（normalized Discounted Cumulative Gain，归一化折损累计增益） | 正确页面越靠前分越高，满分 1。 |
| Wilson 区间 | 比例的 95% 置信区间，题少时很宽。 |

## 3. 为什么要合成题，做出了什么

65 道公开题是外部对照，不能拿来调参（设计 14.2）；而且 65 题只能分辨大约 9 个百分点的差别，P0-13 的调参结论一直等着开发集确认。这次做出来的东西：

| 文件 | 内容 |
|---|---|
| `evals/datasets/hf_docs/synthetic_dev.jsonl` | 开发集 100 题 |
| `evals/datasets/hf_docs/synthetic_holdout.jsonl` | 保留集 100 题 |
| `evals/datasets/hf_docs/synthetic_manifest.json` | 出题和打分的模型、提示词版本、两个抽样种子和拆分种子、过滤门槛、每一步的题数、被去掉的原因、两个文件的 sha256 |
| `evals/datasets/hf_docs/NOTICE.md` | 许可说明：来自 MIT 许可的语料 `m-ric/huggingface_doc`，按 MIT 分发 |
| `src/rag/eval/synthetic/` | 抽段、出题、打分、过滤、拆分的代码和命令 `python -m rag.eval.synthetic` |

每道题标注到页面（`relevant_pages` 是来源页面的 doc_id），和公开题一样，可以直接交给检索评测的 `run --questions`。题目的 `meta` 里还存了原文段落、三项分数和打分理由、照抄检查的结果。

流程（数字是这次的实际数）：

```
2,617 页清洗后的页面
  │ 去掉 48 页中文、64 页公开题的来源页
  ▼
按层抽段：第一批 420 段（种子 0），试跑 20 段，再追加 380 段（种子 1）
  │ 抽段时跳过 171 页太短、364 页几乎全是代码、1 页模板文字（跳过的页从同一层另取）
  ▼
800 段 ──deepseek-v4-flash 出题──▶ 799 题（1 段输出格式不对）
  │
  ▼  qwen/qwen3.6-flash 三项打分（2,397 次）
  │  三项都不低于 4 分、不照抄、答案不超过 300 字符、不重复
  ▼
200 题 ──按层、种子 0 对半拆──▶ 开发集 100 题，保留集 100 题
```

几个做法的理由写在 `docs/decisions.md`（2026-10-18 P1-05 的几条），这里只列结论：
- 从页面原文截段，不从索引的块截，换切块大小时题目不偏向现在的切法。
- 公开 65 题的来源页面不出合成题，开发集调参时不会间接照着公开题调。
- 只用英文页面。
- 出题和打分用两家的模型（DeepSeek 和阿里）。

## 4. 花了多少钱

价格都是配置里的偏高估计：输入每百万 token 2 元，输出 8 元，两个模型一样。

### 4.1 事先的估计（写在 spec 里，跑之前）

| 项 | 估计的 token | 估计花费 |
|---|---|---|
| 出题 420 次 | 每次输入约 750，输出约 500（其中思考约 400），另加 10% 重试 | 2.5 元（输出 1,000 时 4.4 元） |
| 打分 420 题乘 3 项 | 每题三次合计输入约 1,400、输出约 300 | 2.2 元（最多 3.2 元） |
| 检索评测的问题向量 | 约 250 题，每题约 25 token | 不到 0.01 元 |
| 合计 | | 约 4.7 元，最多 7.6 元 |

### 4.2 试跑 20 段以后的推算

试跑：出题每段 0.0059 元，打分每题 0.0052 元，按这个推算 420 段共 4.67 元，和估计一致。但 20 题只留下 6 题（30%），420 段只能留下约 126 题，凑不够开发集和保留集各 100 题。按 30% 算要 670 段左右才够，于是追加 380 段，共 800 段，推算再花约 4.2 元，花费记录预计到 13 元左右，离 28 元的停止线很远，所以继续跑。

### 4.3 实际花费

| 项 | 调用次数 | 输入 token | 输出 token（其中思考） | 花费 |
|---|---|---|---|---|
| 出题 | 800 | 558,542 | 525,038（500,492） | 5.32 元 |
| 打分 | 2,397 | 926,190 | 277,490（0） | 4.07 元 |
| 两次中途停掉时已经发出、结果没写进记录的调用 | 116 | | | 0.30 元 |
| 检索评测的问题向量（200 题） | | | | 不到 0.01 元 |
| 合计 | | | | 9.69 元 |

花费记录里的总额从 3.502 元变成 13.195 元，离 28 元的停止线还有 14.8 元。

估计和实际的差别：
- 出题每次的输出 token 是 656 个，比估计的 500 多三成；其中 626 个是思考，真正写出来的问题和答案只有约 30 个 token。每段 0.0066 元，比估计的 0.0059 元多一成。
- 打分每题 0.0051 元，和估计一致。
- 总花费比估计多一倍，原因是段数从 420 加到了 800；按 800 段算，事先估计的单价对出题低了一成，对打分是准的。
- 没写进记录的 0.30 元：一次是每批都调一次 `asyncio.run`，模型的连接属于第一个事件循环，第二批开始报错（P1-04 的裁判也出过同样的问题，已经修好并加了测试）；一次是同时发 16 个打分请求时网关连续拒绝连接，进程停住不动（连接池里的连接全被占着，2 分钟没有一次调用成功），停掉以后用 4 个并发接着跑。两次停掉时正在进行的调用已经花了钱，但结果没写进记录。

## 5. 每一步剩下多少题，去掉的原因

### 5.1 三项打分的分布（799 题）

| 分数 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 能不能从原文答出来 | 1 | 0 | 0 | 2 | 796 |
| 对开发者有没有用 | 221 | 270 | 42 | 212 | 54 |
| 不看原文能不能看懂 | 185 | 23 | 0 | 8 | 583 |

「能不能答出来」几乎都是 5 分：出题模型只看这一段写题，题目基本都能从这段答出来，这一项过滤不掉什么。真正去掉题的是另外两项。

### 5.2 去掉的原因

一道题可能同时有几个原因，下表每个原因单独计数：

| 原因 | 题数 | 只因为这一条被去掉 |
|---|---|---|
| 对开发者有没有用低于 4 分 | 533 | 355 |
| 不看原文能不能看懂低于 4 分 | 208 | 45 |
| 照抄原文（连着超过 6 个词相同） | 37 | 16 |
| 重复问题（一字不差） | 6 | 2 |
| 能不能答出来低于 4 分 | 1 | 0 |
| 出题输出格式不对 | 1 | 1 |
| 留下 | 200 | |

799 题里去掉 599 题（75%），比 HF 原文说的「大约一半」多。主要原因是打分模型给「有没有用」打分很严，例如这些题都被打了 1 到 2 分：

- Where does Aim store its tracked experiments?
- Which organization released the EfficientNet model?
- What Git LFS command tracks TensorBoard event files in a model repository?

公开 65 题的「有没有用」平均只有 3.37 分，说明 HF 发布的题集里本来也有不少 3 分以下的题。如果把这一项的门槛降到 3 分，800 段能留下 235 题（现在是 202 题，再去掉重复题是 200 题），多得不多，所以照 HF 的条件保持 4 分（理由见 `docs/decisions.md`）。

「不看原文能不能看懂」打低分的题，典型是题目里藏着「这个例子」「这个项目」，例如：

- What validation accuracy does the ViT image classification example achieve on imagenette?

照抄检查只去掉 37 题（799 题的 4.6%）。出题提示词里加了「用自己的话写、不照抄原文」，大部分题已经换了说法（第 7 节）。

## 7. 题目是不是太容易

设计 14.2 提醒过：模型照着原文出题，用词和原文高度重合，关键词检索很容易找到，前期在 MT5 手册上这样出的题 Hit 到了 0.989 和 1.000，什么改动都量不出来。这次从两方面看。

### 7.1 用词重合

拿每道题和它的来源页面整页比（公开题也这样比，两边可以对照）：

| 题集 | 题数 | 最长连续相同词数的中位数 | 达到 7 个词以上的题 | 题里的实词在页面里出现的比例（中位数） |
|---|---|---|---|---|
| 公开 65 题 | 64（015 的页面不在清洗后的页面里） | 4 | 12.5% | 0.88 |
| 开发集 | 100 | 3 | 0% | 0.83 |
| 保留集 | 100 | 3 | 0% | 0.80 |

合成题和原文的重合比公开题还少。实词是去掉 what、is、the 这类词以后的词；库名、函数名、参数名照原样写，所以这个比例本来就不会很低。

### 7.2 关键词检索第 1 名就找对的比例

规则：关键词检索单独那一路的 Hit@1 达到 0.95 以上，就说明题目太容易。

| 题集 | 关键词检索 Hit@1 | Wilson 区间 |
|---|---|---|
| 公开 65 题 | 0.754 | 0.64 到 0.84 |
| 开发集 | 0.570 | 0.47 到 0.66 |
| 保留集 | 0.500 | 0.40 到 0.60 |

远低于 0.95，也比公开题低，题目不是太容易。关键词检索这一路的数字取自下一节同一次运行里这一路自己的列表（重排之前）。

## 8. 现在的检索在三个题集上的分数

配置和 P0-13 定下的一样：标题乘 1，两路权重相等，送重排 10 段，阈值 0.3，最终最多 8 段，一次一个请求。三次运行都在 git 提交 28b340c 和 5fd654d 上（两个提交之间检索代码没变）；开发集和保留集两次运行时 spec 文件有未提交的改动，记录里标了 dirty，这个改动不影响检索。

| 指标 | 公开 65 题 | 开发集 100 题 | 保留集 100 题 |
|---|---|---|---|
| Hit@1 | 0.831（0.72 到 0.90） | 0.660（0.56 到 0.75） | 0.670（0.57 到 0.75） |
| Hit@3 | 0.938 | 0.830 | 0.820 |
| Hit@5 | 0.985 | 0.880 | 0.870 |
| Hit@8 | 0.985（0.92 到 1.00） | 0.890（0.81 到 0.94） | 0.880（0.80 到 0.93） |
| MRR@8 | 0.896 | 0.753 | 0.753 |
| nDCG@8 | 0.919 | 0.787 | 0.785 |
| 关键词检索这一路 Hit@1 | 0.754 | 0.570 | 0.500 |
| 向量检索这一路 Hit@1 | 0.646 | 0.480 | 0.440 |
| 整条检索链 P50 / P95 | 3.2 秒 / 4.1 秒 | 3.1 秒 / 3.4 秒 | 2.8 秒 / 3.1 秒 |
| 重排超时、只有一路检索返回（`degraded`） | 0 | 0 | 0 |

看到的情况：
- 开发集和保留集的分数几乎一样（Hit@1 差 1 个点），两套题难度相当，拆分没有偏。
- 合成题比公开题难：Hit@1 低 16 到 17 个点，Hit@8 低约 10 个点。公开题大多是 HF 用人工审过的、和原文用词更接近的题（第 7.1 节）。
- 两路各自的排序：在三个题集上都是关键词检索比向量检索好，P0-13「标题乘 1 以后关键词检索比向量检索好」的结论在开发集上也成立。
- 100 题能分辨多大的差：按精确 McNemar 检验，至少要 6 题变好、0 题变差（6 个百分点）才算可靠，比 65 题的 9.2 个点好一些。

### 8.1 三路都没找到的 7 题：查下来都是标注问题

按设计 14.2，所有配置都没命中的题先查标注。开发集 3 题、保留集 4 题，最终列表、关键词检索、向量检索的前 8 名里都没有标注页面。逐题看过：

| 问题 | 标注页面 | 情况 |
|---|---|---|
| Which parameter in timm.create_model specifies the number of classes for finetuning?（开发集；保留集有一道几乎一样的题） | timm 的 pnasnet、tf-mobilenet-v3 模型卡 | timm 一百多个模型卡页面都有同一段微调说明，答案不只在标注页 |
| What PyTorch function is used to get the top 5 predictions from probabilities?（开发集；保留集也有一道） | timm 的 inception-v4、inception-resnet-v2 模型卡 | 同上，每个模型卡都有同一段 `torch.topk` 代码 |
| What function loads a dataset from the Hugging Face Hub? | 课程字幕第 5 章 | Datasets 文档的 `loading.mdx` 讲得更直接，检索排在第 1 |
| How many classes does the GLUE MRPC dataset have? | 课程字幕第 3 章 | 课程正文第 3 章第 2 页也有，检索排在第 1 |
| What is the highest-level API in the Transformers library called? | 课程字幕第 1 章 | 很多页都讲 pipeline |

这 7 题的问题不是这一页独有的，和公开题 015 是同一类标注问题。粗略估了一下有多少题受影响：拿每道题原文段落中间的 200 个字符去其他页面里找，200 题里有 33 题（开发集 15、保留集 18）在别的页面上找到了一模一样的文字。只看另外 167 题，开发集 Hit@1 是 0.718、Hit@8 是 0.929，保留集 Hit@1 是 0.695、Hit@8 是 0.902。

## 9. 局限

- 标注只有来源页一页。约六分之一的题（33 题）的原文在别的页面上也有，正确答案不止一页，指标会被低估；三路都没找到的 7 题都是这一类。
- 开发集和保留集之间有 2 对意思相同的题（timm 的 `num_classes`、token classification 的标签 O），timm 模型卡页面内容几乎一样，分到两边的题会重复。另有 1 对出自不同模型卡、问法相近（SelecSLS42B 和 CSPResNeXt 的模型名）。数量少，对整体数字影响不大，但保留集不完全独立。
- 「有没有用」这一项把 67% 的题打成 3 分以下，过滤后的题偏向打分模型认为「通用」的问题。题目分布和真实用户的问法还有差距，要靠以后的人工题和真实提问补（设计 14.2）。
- 出题模型 `deepseek-v4-flash` 和被测的回答模型是同一个。这次只拿来评检索，没有影响；拿合成题评回答时要换出题模型。
- 「能不能从原文答出来」几乎全是 5 分，这一项没有起到过滤作用，题目的答案对不对没有人工核对过。
- 合成题只有一种：一句话能答的事实题。两跳题、表格题、缩写题都没有。

## 10. 下一步建议

1. 改标注：每道题的标注加上原文相同的其他页面（比如段落中间那段文字也出现的页面），或者把这些题从页面指标里去掉，方法和公开题 015 的 `label_overrides.jsonl` 一样；改完重算开发集和保留集的分数。
2. 去掉跨集合的重复题：拆分前按问题的实词重合度把意思相同的题放进同一边。
3. 用开发集确认 P0-13 的几个选择（标题乘 1、两路权重相等、送重排 10 段、阈值 0.3），再改代码里 `title_boost` 的默认值。
4. 人工抽 20 到 30 题核对答案对不对，估一下合成题本身的错误率。
