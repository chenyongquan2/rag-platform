# P7 报告：模型选型（缩小版）

## 1. P7-01 在 HF 文档知识库上比重排模型、回答模型和向量模型

日期：2026-10-22，分支 `spec/P7-01-model-selection`。原始记录在 git 忽略的 `data/reports/p7-01/`（检索评测记录 `public/`、重排耗时 `curve/`、阈值分数 `scores/`、回答记录 `answer-eval/`、引用核对 `support/`、小索引比较 `embed_small.json`、运行日志 `*.log`）。

### 1.1 这一节回答什么

设计第 19 章的 P7 要求每一层模型出一张选型表：指标、延迟、成本，加上和现在用的模型逐题配对的检验结果。计划表（`docs/plan.md` 第 29 行）把它缩小成下面这些：

1. 重排模型：现在的 `BAAI/bge-reranker-base` 和两个能在本机 CPU 上跑的模型比，用 99 道开发集题，看 Hit@1、Hit@8、MRR、每题重排耗时。不花钱。
2. 回答模型：从网关上选两个便宜的、和裁判不是同一家的模型，和现在的 `deepseek-v4-flash` 在同一批检索结果上比 65 道公开题：全对的题数、引用准不准、格式对不对、耗时、每题花费。
3. 向量模型：不重建索引。只估算换一次要多少钱、多长时间，写清楚换的步骤；再用一个小语料粗略比较一次。
4. 裁判模型：不换，写清楚要比裁判还缺什么。

所有默认值都没有改。下面每一层的建议只是建议，换不换由你定。

### 1.2 先说几个词

| 词 | 意思 |
|---|---|
| 重排模型 | 把检索出来的候选段和问题一对一对地打分、重新排序的模型（Cross-Encoder，一次读问题和一段正文）。现在每题送 10 段进重排（`rerank_n: 10`）。 |
| 开发集 | P1-05 生成的 99 道合成题（`synthetic_dev.jsonl`），用来做选择。保留集这次没有用。 |
| Hit@1、Hit@8 | 排在第 1 位的页面（或前 8 个页面里有一个）是标准答案页面的题所占的比例。 |
| MRR@8 | 标准答案页面在前 8 名里第一次出现的名次的倒数，再对所有题取平均；没出现记 0。 |
| McNemar 检验 | 只看「一个模型对、另一个错」的题，算这种分布偶然出现的概率 p。用于 Hit、全对这类只有对错两种结果的指标。 |
| 置换检验 | 把每道题两个模型得分之差的正负号随机翻很多次，看实际的平均差在随机结果里算不算少见。用于 MRR、裁判分这类连续的指标。 |
| 可靠的差别 | p 不大于 0.05。p 没有按「同时看了好几个指标」做校正。 |
| 误拒 | 有答案的题，所有段的重排分都低于阈值，检索直接返回「没找到」（P2-02 用的说法）。 |
| 全对 | 裁判模型（`qwen/qwen3.6-flash`，P1-04 的提示词 `p1-04-hf-v1`）在 1 到 3 分里给 3 分。 |
| 每句都标了编号 | 回答给出了内容，而且每一句后面都有一个合法的片段编号，例如 `[1]`（P1-04 的格式检查，设计 11.2 第一层）。 |
| 引用精确率、召回率 | P1-06 的引用核对（设计 11.2 第二层）：裁判模型逐对判断「这一句」和「它引用的这一段」，精确率是被判「支持」的对所占的比例，召回率是至少有一段支持它的句子所占的比例。 |
| 网关超时 | 回答模型的调用在连接网关时超时（`llm_timeout`）。这次网关的连接很不稳，同一时间连 `/models` 和测试调用也会超时，所以这类失败不算模型答错，重新问一遍（见 1.6）。 |

### 1.3 这些题集能分辨多大的差别

- 99 道开发集题：Hit 这类对错指标要差 6.1 个百分点以上才可能可靠（最好的情况是 6 题变好、0 题变差，p = 0.031）。
- 65 道公开题：要差约 8 到 10 个百分点（设计 14.4）。现在的回答模型在这 65 题上已经是 64 题全对（98.5%），比它好的模型最多只能多对 1 题，**这批题分不出「更好」，只能分出「明显更差」**。
- 每个模型只跑了一遍，没有重复测量。

### 1.4 重排模型

**做法。** 同一条检索链（`make_search_pipeline`，和 search_docs 一样：BM25 和向量两路融合，取前 10 段送重排，阈值 0.3，最终最多 8 段），只把环境变量 `RERANKER_MODEL` 换成候选模型，跑 `python -m rag.eval.retrieval run` 和 `rerank-curve`（脚本 `scripts/p7_01/rerankers.py`）。真实索引只读，问题向量来自 Redis 第零层缓存，重排模型从本机缓存离线加载（`HF_HUB_OFFLINE=1`）。所以三个模型拿到的 10 个候选段完全一样，差别只来自重排。

**候选。**
- `cross-encoder/ms-marco-MiniLM-L-6-v2`：约 2,200 万参数，只认英文，在 MS MARCO 上训练，比现在的模型小很多。
- `BAAI/bge-reranker-v2-m3`：约 5.7 亿参数（下载 2.29 GB），多语言，是现在这个模型的后继版本。
- `BAAI/bge-reranker-large` 没有比：它和 v2-m3 差不多大，v2-m3 在 CPU 上已经慢到不能用（见下表），再比一个同样大小的模型没有意义。

模型都从 `https://hf-mirror.com` 下载，只下载 safetensors 格式的权重和配置文件，加载时不执行模型仓库里的代码（`trust_remote_code=False`）。

**结果（99 道开发集题，页面级，最终列表）。** 「对现在的模型」一栏写的是：候选模型对、现在的模型错的题数，现在的模型对、候选模型错的题数，以及 p。

| 重排模型 | Hit@1 | 对现在的模型 | Hit@8 | 对现在的模型 | MRR@8 | 对现在的模型 | 结论 |
|---|---|---|---|---|---|---|---|
| bge-reranker-base（现在） | 0.788 | | 0.929 | | 0.841 | | |
| MiniLM-L-6 | 0.707 | 2 题变好、10 题变差，p = 0.039 | 0.929 | 2 题变好、2 题变差，p = 1.0 | 0.787 | 7 题变好、17 题变差，p = 0.026 | Hit@1 和 MRR 可靠地变差 |
| bge-reranker-v2-m3 | 0.768 | 4 题变好、6 题变差，p = 0.75 | 0.939 | 2 题变好、1 题变差，p = 1.0 | 0.834 | 6 题变好、11 题变差，p = 0.75 | 没有可靠差别 |

同一个 bge-reranker-base 跑了两遍（06:00 和 07:31），99 道题的结果逐题完全一样。第一遍里有一道题的问题向量请求在连接网关时超时，只用了 BM25 一路检索，结果仍然一样。

**重排耗时（只算重排这一步，送 10 段，先跑 3 道题预热不计时）。** 这台机器上同时还有别的工作区在跑，CPU 占用一直在变，所以绝对数字只能看大概，**看倍数更可靠**。括号里是测量开始前的整机 CPU 占用。

| 重排模型 | 中位数 | 第 95 百分位 | 每个候选段 | 整条检索链的中位数 |
|---|---|---|---|---|
| bge-reranker-base | 3.48 秒（31%）；另一次 2.67 秒（55%，当时我自己在跑单元测试） | 4.81 秒；另一次 2.92 秒 | 约 0.26 到 0.38 秒 | 2.87 秒 |
| MiniLM-L-6 | 0.50 秒（74%）；另一次 0.57 秒（37%） | 0.82 秒；另一次 1.63 秒 | 约 0.05 到 0.08 秒 | 0.49 秒 |
| bge-reranker-v2-m3 | 9.55 秒（44%） | 12.79 秒 | 约 0.96 秒 | 9.41 秒 |

- MiniLM 比现在的模型快约 5 到 7 倍，但 Hit@1 少了 8 个百分点，而且是可靠的变差。
- v2-m3 比现在的模型慢约 3 倍，每题重排要 9 到 13 秒，远远超过 search_docs 第 95 百分位 3 秒的目标；效果没有可靠差别（Hit@8 多 1 题，Hit@1 少 2 题）。
- 两个候选都没有赢，所以**阈值不用重定**，`threshold: 0.3` 和 `reranker_model` 都不改。

**为什么换重排模型就要重定阈值。** 计划要求换模型以后用 P2-02 的脚本重新定阈值。MiniLM 没有赢，但它的分数正好能说明为什么不能照搬 0.3：两个模型的分数都经过 sigmoid 换算到 0 到 1 之间，可分数的分布不一样。用 P2-02 的脚本（`rag.eval.threshold collect` 再 `sweep`）在同样的题上量了两个模型：

| 同样用阈值 0.3 | bge-reranker-base | MiniLM-L-6 |
|---|---|---|
| 开发集被误拒的题 | 0/99 | 0/99 |
| 开发集平均每题留下的段 | 5.6 | 6.4 |
| 50 道无答案题里没被拒绝的题 | 25/50 | 26/50 |
| 按设计 10.2 的规则选出的阈值（开发集误拒不超过 2%，在这个前提下无答案题拒绝得最多；候选阈值步长 0.1） | 0.7（误拒 1/99，无答案题放过 16/50） | 0.7（误拒 0/99，无答案题放过 19/50） |

- 同一个 0.3，MiniLM 每题多留下约 0.8 段，因为它给不相关段的分数整体偏高；阈值 0.8 时，现在的模型误拒 3 题，MiniLM 误拒 4 题，误拒开始出现的阈值也不一样。所以换模型以后，阈值要按新模型的分数重新量，不能沿用旧值。
- 现在这个模型在 0.3 上的数字和 P2-02 报告的完全一样：99 道开发集题误拒 0 道，94 道里丢了 2 道的正确页面，平均每题留 5.6 段，原来那 30 道无答案题放过 14 道，说明这次的脚本和数据没有走样。
- 50 道无答案题是 P2-02 的 30 道加上 P3 的 20 道难题（`no_answer_hard.jsonl`）。v2-m3 的分数没有收集：它没有赢，收集一遍要再跑约 1 小时 CPU。

### 1.5 回答模型：选了哪两个，为什么

网关的模型列表（`/models`，61 个模型）里，便宜的、和裁判（阿里的 qwen）不是同一家的模型有：

| 模型 | 厂家 | 这次的情况 |
|---|---|---|
| `google/gemini-3.5-flash-lite` | Google | 用了。不是推理模型，测试调用 2.0 秒。 |
| `z-ai/glm-5.3-flash` | 智谱 | 用了。测试调用 2.6 秒；这次返回的 `total_tokens` 等于输入加输出，`docs/decisions.md` 记过的「有看不到的思考 token」这次没有出现。 |
| `minimax/minimax-m3.1-flash` | MiniMax | 没用。两次测试调用都等满 60 秒超时，账本按取消时的估计记了 0.066 元。 |

两个候选和现在的回答模型用同一个价格估计（输入每百万 token 2 元、输出 8 元，`estimated: true`），所以下面的「每题花费」比的是 token 用量，不是真实价格。网关这次在这两个模型的返回里带了一个 `cost` 字段（例如 glm 29 个 token 是 5.4e-06，gemini 20 个 token 是 2.14e-05），单位没有写明，`deepseek-v4-flash` 的返回里没有这个字段，所以没有拿它算钱。

### 1.6 回答模型：怎么比的

- **现在的模型（基线）**：P3-07 今天在 `main` 上跑的标准 RAG 记录里那 65 道公开题（`deepseek-v4-flash`，裁判第一遍，引用核对第一遍；数据在 `C:/workspace/rag-platform-data/p3-07/`）。其中 4 道第一遍是网关超时，P3-07 已经单独重新问过（`p3-07-retry/`），这里用重新问的结果。这 4 道重新问的回答没有做引用核对，所以基线的引用精确率只算 60 个回答。
- **候选模型**：`python -m rag.eval.answer run` 用同一条检索链和同一个回答提示词（P1-04 的标准 RAG）。gemini 先跑，检索现场做；glm 用新加的 `--contexts-from` 直接拿 gemini 那次每题的段，所以两个候选看到的段完全一样，也不用再跑重排。和基线比：65 题里 63 题交给回答模型的页面和顺序都一样，`qa_eval:011`、`:012` 两题有一两个页面不同（P3-07 跑这两题时重排超时了）。去掉这两题再算一遍，结论不变：剩下 63 题里，基线 62 题全对，gemini 59 题全对（p = 0.25），glm 62 题全对。
- **网关超时重新问**：gemini 第一遍 7 题、glm 第一遍 4 题网关超时。用新加的 `--retry-errors` 只把这些题拿同样的段重新问一遍（glm 有 1 题问了两遍才成功），合并成一份记录再打分。基线也是同样处理的（上面那 4 道），三边规则一样。
- 裁判、引用核对用的模型和提示词和 P3-07 完全一样，都只打了一遍。

| 每个回答的召回率，配对 | | 58 题配对：1 题变好、1 题变差，p = 1.0 | |

- 三个模型都答错 `qa_eval:015`，这题的正确页面检索没找到（P3 报告记过），和回答模型无关。
- gemini 多错的 3 题：2 题在段里有答案时说「文档里没有」，1 题（`qa_eval:019`）答错。3 题变差、0 题变好，p = 0.25，方向是变差，但 65 题分辨不出来。它的引用精确率低一些（90.3% 对 96.2%，区间有重叠，两边的引用对不是同一批，不能配对检验）：它平均每句引用 1.6 段，一句话引了几段时，有的段只支持一半（124 对里 11 对被判「部分支持」）。
- glm 和现在的模型在 65 题上逐题一样（都是 64 题全对、错的是同一题）。回答这一步的中位数快一半（1.58 秒对 3.16 秒），第 95 百分位差不多。花费少约 17%，主要因为它几乎不输出思考 token（65 题共 304 个，`deepseek-v4-flash` 每题约 80 个）。耗时是不同时间测的（基线是 P3-07 在 12 点前后跑的），网关当时的快慢会影响这个数。
- glm 在网关上超时得多：65 题第一遍有 4 题超时，gemini 7 题；P3-07 里 `deepseek-v4-flash` 是 150 题 4 题。这次是网关整体不稳的时段，三边不是同一时间跑的，不能拿来比哪个模型更稳。

### 1.8 向量模型：换一次要多少钱、多长时间

**网关上没有第二个向量模型。** `/models` 里唯一的向量模型就是现在用的 `qwen/text-embedding-v4`。所以要换，只能用本机模型或者别的服务商，这次只能估算，也只用本机模型粗略比较了一次。

| 项 | 数字 | 出处 |
|---|---|---|
| 要重新算向量的段 | 26,372 段 | P0-12 |
| 这些段的 token | 5,196,039 | P0-12 的账本 |
| 用网关模型算一遍的钱 | 按每百万 token 0.5 元是 2.60 元，多算 15% 防止估少是约 3.0 元；换成别的模型就是 5.2 乘以它每百万 token 的价格 | P0-12 价格 |
| 用网关模型算一遍的时间 | 同时发 4 个请求每分钟约 1,035 段，约 26 分钟，再加重建写入约 5 分钟 | P2-03 第 2.8、2.9 节 |
| 本机 `BAAI/bge-base-en-v1.5`（CPU）算一遍的时间 | 这次量到每秒 3.5 段，推算约 2.1 小时；量的时候 CPU 被重排评测占满（85% 到 100%），空闲时应该更快，没有量 | 本节下面的小语料实验 |
| 题集的问题向量 | 几百道题，每题约 20 个 token，不到 0.01 元 | |

**小语料粗略比较（明确是近似，不能当作真实索引上的结果）。** 脚本 `scripts/p7_01/embed_small.py`，不写 Elasticsearch，在内存里做精确的余弦相似度检索：语料是 99 道开发集题的标准答案页面的全部段（195 页、2,085 段），加上随机抽的 2,000 段别的段（随机种子 0），一共 4,085 段，只有真实索引的 15%。干扰段少，题会比真实索引容易得多，所以只看两个模型的差，不看绝对数。只用向量一路，没有 BM25 和重排。现在的模型用缓存里的向量（不花钱，问题向量全部来自 Redis 缓存），对照模型 `BAAI/bge-base-en-v1.5`（每个向量 768 个数，只认英文，问题前面加它要求的检索提示语）在本机 CPU 上现算。

| 指标 | qwen/text-embedding-v4（现在） | bge-base-en-v1.5 | 配对 |
|---|---|---|---|
| Hit@1 | 0.778 | 0.747 | 10 题变好、13 题变差，p = 0.68 |
| Hit@8 | 0.970 | 0.939 | 1 题变好、4 题变差，p = 0.38 |
| MRR@8 | 0.851 | 0.810 | 平均差 -0.042，p = 0.20 |

没有可靠差别，方向是本机模型差一点。原来打算用的 `BAAI/bge-m3`（多语言，每个向量 1024 个数）在镜像上没有 safetensors 格式的权重，只有要用 pickle 加载的文件，所以没有下载，换成了 bge-base-en-v1.5。

**换向量模型的步骤（照 P2-01 的别名切换，没有实际做过；下面几处问题是读代码发现的）。**
1. 向量模型是服务级的设置（`EMBED_MODEL`、`EMBED_DIM`），三个知识库共用。换模型要三个知识库都重建，或者先把向量模型改成每个知识库各自的配置。
2. 只在重建进程里设新的 `EMBED_MODEL` 和 `EMBED_DIM`，跑 `python -m rag.index.cli rebuild --kb hf_docs --all`：建 `v(N+1)`、写入、补一次增量同步、合并段、过检查，然后切别名。新模型的向量长度不同时（比如 bge-base 是 768 个数，现在是 1024 个数），新索引的映射本来就不一样，必须新建版本。摄取任务会把模型名写进索引的 `_meta.embed_model`，往存着别的模型向量的索引里写会直接报错（`IndexModelMismatchError`），所以不会把两种向量混进一个索引。
3. **查询这一边没有这层检查。** `src/rag/retrieve/` 里算问题向量时用的是服务进程自己的 `EMBED_MODEL`，不看别名后面那个索引的 `_meta.embed_model`。别名切过去、服务还没换成新模型重启的这段时间里：向量长度相同时，检索会拿旧模型的问题向量去查新模型的段向量，排序是错的，但不会报错；长度不同时 kNN 查询会出错（没有实测会退成只用 BM25 还是直接报错）。所以切别名和用新模型重启服务要在同一次维护里做；更稳的做法是先补一个检查：问题向量的模型和索引记的模型不一致时，退成只用 BM25 并标 `degraded`。
4. 现在的检查只比较段数（`chunk_count_gate`），不评测检索效果（设计 7.5 要的评测检查还没做，P2-03 记过）。换模型前要先在新索引上跑一遍开发集检索评测，Hit@1 没有变差再切。
5. 切换以后：第零层问题向量缓存按模型名分开存，旧的自然不再命中；结果缓存跟着数据代号失效；P5 的语义缓存存的是旧模型的问题向量，要清掉，距离阈值 0.06 要按新模型重新定（设计 19 章 P7 那一行）。回滚用 `python -m rag.index.cli rollback --kb hf_docs`，同时把服务的 `EMBED_MODEL` 改回旧值重启。

### 1.9 裁判模型

不换。裁判还是 `qwen/qwen3.6-flash`，设置和 P1-04 一样（温度 0，`enable_thinking: false`）。要比两个裁判，得有人工打分作参照：设计 14.3 要每个知识库 50 条人工打分，再看裁判和人工的加权 kappa。P1-04 和 P3-05 已经导出了人工打分表（`human_sheet.csv`），还没有人打分。没有人工分数，只能比两个裁判彼此一不一致，说不出哪个更准，所以这次没有比。

### 1.12 局限和没核实的

- 只用了 HF 文档这一个知识库；开发集是合成题，回答比较用的是 65 道公开题；每个模型只跑了一遍；保留集没有用。
- 回答这一层的题太容易：现在的模型在这 65 题上 64 题全对，候选模型最多多对 1 题，所以这批题只能看出「明显更差」。
- 基线和两个候选不是同一时间跑的（基线来自 P3-07），回答耗时会受网关当时快慢的影响；网关这次超时很多，三边都按同样的规则重新问了超时的题。
- 重排耗时受同一台机器上别的工作区影响很大：同一个模型两次量到的中位数是 2.67 秒和 3.48 秒。MiniLM 的一次测量开始前 CPU 占用是 74%，高于 60% 的要求，所以又在 37% 时量了一次，两次都写在表里。
- glm 的引用精确率、召回率没有量。
- v2-m3 的阈值分数没有收集（它没有赢）。
- 本机向量模型的速度是在 CPU 很忙时量的；小语料只有真实索引的 15%，比真实情况容易。
- 1.8 第 3 步「查询端不检查索引记的向量模型」是读代码得出的，没有实际切换过别名去验证。
- 网关返回里的 `cost` 字段单位不明，没有核实，没有用。
