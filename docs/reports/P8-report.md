# P8 报告：上线准备（P8-01）

规格：`specs/P8-01-production-readiness.md`。每一项为什么这么做见 `docs/decisions.md` 的「P8-01：上线准备」。下面的数字都是 2026-10-21 晚到 10-22 凌晨在本机测的：8 核 16 线程、32 GB 内存、没有 GPU，Elasticsearch 和 Redis 是几个工作区共用的那一套。

## 2. 权限隔离检查

### 2.1 怎么测的

命令 `uv run python -m rag.eval.access --questions 3`。服务按真实配置启动（三个真实索引，只读；真实的重排模型；结果缓存开着），用 OAuth 模式，两个调用方：

- `local`：能用三个知识库，文档权限组是 public 和 internal；
- `guest`：只能用 hf_docs，权限组是 public。

每个知识库取 3 个问题（hf_docs 和 pdf_demo 来自评测集，mt5 没有评测集，用 3 个手写的问题）。每个调用方对每个问题调 search_docs、ask_docs 和流式 ask_docs；`guest` 再对 `local` 拿到的每个私有段调 get_context；两个调用方都调 list_knowledge_bases。最先做缓存检查：`local` 把一个新问题问两次，第二次应当命中缓存；`guest` 再问同一个问题，不能拿到 `local` 的缓存。

「泄露」的定义：任何回答里出现了这个调用方不能用的知识库的段编号（正文段、来源、最接近的段、阈值以下的段、流式事件里的都算）。对不能用的知识库，回答必须和不存在的知识库一样是 `kb_not_found`，回 200 就记一次「暴露」。对话模型是假的，不花钱。

### 2.2 结果

第一次运行时 Redis 里没有任何缓存的查询向量（Redis 不持久化，之前被重启过），查询向量网关的地址被换成了没有服务的端口，所以 36 个请求只用 BM25 检索，缓存检查也没法做（只用一路的结果按设计不写缓存）。泄露仍然是 0。于是用真网关算了这 92 个问题的向量（约 0.0009 元），再跑一次：

| 数字 | 第二次运行 |
|---|---|
| 请求数 | 105 |
| 返回的段数 | 195 |
| 泄露的段数 | 0 |
| 不可见知识库的暴露次数 | 0 |
| 应当成功却失败的请求 | 0 |
| 只用一路检索的请求 | 4（ask_docs 改写后的问题没有缓存的向量） |
| 缓存：同一调用方第二次命中，另一个权限组的调用方没有命中 | 是 |
| `guest` 对 `local` 看到的私有段调 get_context | 46 次，全部 `kb_not_found` |
| 加载重排模型的时间、总时间 | 54 秒、205 秒 |

完整的表在 `data/reports/p801-access-warm.md`（不进仓库）。

### 2.3 文档级权限（真实数据测不出，另写了集成测试）

三个真实索引的所有文档权限组都是 public，所以上面的检查只能证明「知识库级别」的隔离。文档级的过滤用集成测试 `tests/integration/test_access_leaks_es.py` 测：把 `fake_kb_hf_docs_v1`（438 段，假向量）用备份工具恢复成测试索引，把 Inference Endpoints 的页面改成 internal 组。结果：`local` 能检索到这些段；`guest` 的检索结果、get_context（chunk、neighbors、page 三种方式）、以及 `local` 填进去的缓存里，都没有这些段。

### 2.4 检查器本身会不会漏

单元测试故意把 mt5 配置成所有人可用，检查器报出了暴露和泄露的段；故意让两个调用方用同样的权限组（等于缓存键不含权限组），检查器报出了「拿到了别人的缓存」。

## 3. 限流、预算、熔断的行为

| 情况 | 结果 |
|---|---|
| 调用方一分钟内超过上限 | HTTP 回 429 `rate_limited`，`Retry-After` 是这一分钟剩下的秒数；MCP 返回错误结果，类别相同；另一个调用方不受影响；下一分钟恢复 |
| Redis 连不上 | 请求照常处理，一分钟最多记一行警告（单元测试和连向不存在端口的集成测试都验证过） |
| 今天的花费加一次 ask_docs 的估计超过调用方或服务的每日上限 | ask_docs 回 429 `budget_exceeded`，`Retry-After` 是到 UTC 零点的秒数，没有调用任何模型；search_docs 照常 |
| 网关连续失败 5 次 | 之后 30 秒内的对话调用不发出去，错误类别仍是 `llm_error`；ask_docs 只返回检索到的段；search_docs 不受影响；30 秒后放一个调用试探 |
| 熔断打开 | 指标 `rag_model_breaker_total{rag_breaker_event="opened"}` 加 1，提醒 `ModelGatewayBreakerOpen` 在下一次计算规则时发出，最后一次被拒绝的调用之后 5 分钟消失 |

令牌校验的单元测试覆盖了：有效令牌、过期、受众不对、签发方不对、签名不对、未知密钥编号、缺少 `exp`、缺少 `aud`、不是 JWT、`alg: none`、用公钥当密钥的 HS256 令牌、还没到生效时间，共 12 种情况；HTTP 和 MCP 两条路都测了没有令牌和坏令牌回 401。

对关键测试做了变异检查（故意把一处代码改错，看测试会不会失败）：11 处改动全部被测试发现。改动包括：不查受众、两个 scope 时不拒绝、HTTP 的令牌检查 `BearerGuard` 放过没有令牌的请求、限流多放一个、Redis 出错时报错而不是放过、去掉预算检查、预算不按日期算、熔断永远不打开、传输层不调熔断器、检查器不数泄露、工具说明列出私有知识库。

## 4. 备份和恢复演练

### 4.1 ES 快照（没有应用）

快照仓库需要 `path.repo`，要重启 Elasticsearch，这台机器上的 Elasticsearch 是几个工作区共用的，规则不允许重启。改动写在 `deploy/elasticsearch/snapshot.override.yml`。在主检出目录执行

```
docker compose --dry-run -f docker-compose.yml -f <工作区>/deploy/elasticsearch/snapshot.override.yml up -d --no-deps elasticsearch
```

的输出是只重建 `rag-platform-elasticsearch-1` 这一个容器（`Recreate`），别的容器不动；`docker compose config` 显示快照目录挂在 `C:\workspace\rag-platform-data\es-snapshots`。执行完 Elasticsearch 仍在运行，没有被重建。应用的步骤和注册仓库、每日快照策略的命令在 README「Production guards」一节。

### 4.2 逻辑备份演练（`kb_hf_docs_v1`，26,372 段）

| 步骤 | 用时 | 结果 |
|---|---|---|
| 导出（只读，时间点视图，带向量） | 186 秒 | 26,372 段，gzip 后 138 MB |
| 恢复到新索引 `p801_restore_hf_docs_v1` | 62 秒 | 26,372 段，新 uuid |
| 校验 | 3 秒 | 数量相同、全部编号相同、抽样 200 段的原文和向量全部相同、5 个 BM25 检索的前 10 名完全相同、3 个 kNN 检索的前 10 名完全相同 |
| 复制 docstore 和向量缓存 | 5 秒 | `kb_hf_docs_v1.json` 44 MB、`fake_kb_hf_docs_v1.json` 0.8 MB、`embeddings.sqlite3` 122 MB（用 SQLite 的备份接口复制） |
| 把 docstore 的副本绑定到新索引 | 不到 1 秒 | 副本里的 `index_uuid` 从 `xqQZvuN2R9mcRTKEA63WYQ` 改成新索引的 uuid，原文件没动 |

3 个 kNN 检索里有 1 个，用来查询的那一段自己不是第 1 名，但两个索引的前 10 名完全一样，应该是有内容相同的段，不是恢复的问题。恢复出来的索引演练完已删除。导出加恢复一共约 4 分钟；P5-02 那次事故后从数据源加向量缓存重建 hf_docs 用了 277 秒，两种办法用时差不多，逻辑备份的好处是不依赖数据源还在。

没有演练的：mt5 和 pdf_demo 的 docstore 不在主检出目录（mt5 的在另一个工作区的 `data/mt5docstore/`），这次只复制了主检出目录里有的文件。

恢复顺序：先恢复成新版本名的索引，再把 docstore 复制成新名字并绑定新 uuid，再放回向量缓存，最后用 `index.cli switch` 切换别名（同时把数据代号加 1）。

## 5. 负载测试

脚本是 `python -m rag.ops.loadtest`：每个并发档位起这么多个协程，一个请求结束马上发下一个，预热几秒后计时。机器 CPU 是整机的平均使用率；服务进程 CPU 是服务进程用掉的整机比例。

### 5.1 假数据（`--dev-fake`，检索耗时设为 0，只测服务本身的开销）

每档 20 秒：

| 并发 | 请求数 | 每秒请求数 | P50 毫秒 | P95 毫秒 | P99 毫秒 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1,952 | 97.6 | 9 | 18 | 44 |
| 4 | 2,955 | 147.8 | 26 | 38 | 69 |
| 8 | 2,955 | 147.8 | 52 | 70 | 89 |
| 16 | 2,940 | 147.0 | 104 | 139 | 169 |

服务本身每秒最多处理约 148 个 search_docs，到并发 4 就到顶了，再加并发只是排队变长。一次请求的服务开销约 9 毫秒。和真实检索的几秒比，这部分可以忽略。这一组的服务进程 CPU 没有测到（取到的是 Windows 上 venv 启动器的进程号，不是真正的 Python 进程），第二组改了。

### 5.2 真实 search_docs

真实索引 `kb_hf_docs`、本机重排模型、结果缓存关掉（否则测的是缓存）、限流关掉、OTel 导出关掉（避免触发监控的延迟提醒）；65 个评测问题的查询向量都在缓存里，不花钱。每档 60 秒：

| 并发 | 请求数 | 每秒请求数 | 重排超时 | P50 毫秒 | P95 毫秒 | P99 毫秒 | 机器 CPU % | 服务进程 CPU % |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 21 | 0.35 | 0 | 2,763 | 3,291 | 3,636 | 85.6 | 44.6 |
| 2 | 20 | 0.33 | 0 | 5,518 | 6,320 | 6,376 | 84.3 | 45.9 |
| 4 | 23 | 0.38 | 9 | 8,657 | 9,894 | 10,001 | 90.0 | 43.4 |
| 8 | 41 | 0.68 | 32 | 9,654 | 10,034 | 10,046 | 90.8 | 43.1 |

结论：

- P95 在 3 秒以内的最大并发：没有。一个请求一个请求地发，P95 也是 3.3 秒，比设计目标 3 秒稍高；和之前测的 4 到 6 秒比好一些（之前是机器更忙的时候测的）。
- 这台机器每秒只能处理约 0.35 个检索请求，瓶颈是 CPU 上的重排：一个请求就用掉约 45% 的整机 CPU，加上 Elasticsearch，整机在 85% 以上。并发 2 时每个请求的时间几乎翻倍，每秒请求数不变，说明请求在排队等重排。
- 并发 4 和 8 时每秒请求数变高，是因为很多请求的重排超时了（41 个里 32 个），超时的请求只按融合顺序返回，质量比完整重排差。不能把 0.68 当成能力。
- 所以现在对外只能说：单机 CPU 重排，同时 1 个请求、每秒约 0.35 个检索。要提高，得减少要重排的段数（`rerank_n`）、换小的重排模型、用 GPU，或者多开几个实例（设计 16.6）。

测试期间另一个工作区也在跑任务，CPU 数字会受影响；测完以后看了一眼，机器是空闲的。

## 6. 没做的、没验证的

- 没有接真的公司登录系统，令牌都是测试密钥签的；令牌内省（introspection）、刷新、撤销都不在范围内。
- 摄取没有 HTTP 接口，所以设计里「摄取用单独的管理员令牌」没有做。
- 设计 16.4 的「按 doc_id 删掉相关 trace」没有做（Langfuse 的删除接口没确认）。
- ES 快照仓库没有应用，快照和 SLM 策略没有真跑过。
- 限流按调用方算，同一调用方下的所有用户共用一个上限。
- 每日预算给正在进行的 ask_docs 预留估计花费只在一个进程里有效（审查第 1 轮以前完全没有预留，审查测到剩 0.03 元时同时发 10 个全部通过）；多个服务进程时仍可能多花。
- 流式回答读到一半断开不算进熔断的失败次数。
- 令牌头的 `typ` 不检查。
- 查询向量网关没有熔断，只有原来的短超时，失败后只用 BM25 检索。
- 本机模式的问答页面 `/` 在 OAuth 模式下用不了（没有登录流程）。
