# P5 报告：缓存和监控

这份报告随 P5 的子需求逐节增加。现在只有 P5-01（缓存）一节；P5-02（监控）做完以后加第二节。

## 1. P5-01 缓存

日期：2026-10-21，分支 `spec/P5-01-cache`。原始记录在被 git 忽略的 `data/reports/p5-01/`（每一步的 JSON、模拟负载的逐请求记录、影子记录）。这一节里的问题都是 HF 文档库的公开问题，没有 MT5 手册的内容。

### 1.1 这一节回答什么

1. 缓存放在哪几层，上线了哪几层，键里有什么，什么时候失效。
2. 哪些结果不写缓存，Redis 出问题时请求会怎样。
3. 缓存真有用吗：命中率多少，省了多少时间，未命中时多付多少。
4. 语义缓存（L2）能不能开：它会把哪些不同的问题当成同一个，错误命中率有多高。
5. 没有量到、没有验证的是什么。

### 1.2 先说几个词

| 词 | 意思 |
|---|---|
| L1 精确缓存 | 两次请求的所有条件都相同（知识库、数据、配置、问题、权限……）时，第二次直接用第一次的结果。存在 Redis 里。 |
| L2 语义缓存 | 两个问题意思相近就算同一个，用第一个问题的检索结果。这次只做「影子模式」。 |
| 影子模式 | 照常检索、照常返回，同时记下「如果开了语义缓存，会用哪个旧问题的结果、对不对」。不改变返回的结果。 |
| 数据代号 | Redis 里每个知识库一个数字，摄取写完、刷新以后加 1。键里带着它，数据变了旧缓存就不再命中。 |
| 误命中 | 把不该共用结果的两个问题当成了同一个。 |
| 反例 | 一对「看起来像、但不能共用缓存」的请求。 |
| Wilson 区间 | 比例的 95% 置信区间。样本少时，观察到的比例不准，区间告诉你真实比例可能在哪个范围。 |
| 熔断 | 连续失败几次以后，一小段时间内不再尝试，免得每个请求都等一次超时。 |

### 1.3 做了什么

```text
search_docs / ask_docs 请求
   │ 1 读这个知识库的数据代号（Redis，约 1.4 毫秒）
   │ 2 算键，读缓存（Redis，约 1.2 毫秒）
   ├─ 命中 ──→ 返回缓存里的结果（请求编号、耗时换成这次的）
   └─ 未命中
        │ 3 同一个键已经有请求在算：等它的结果（进程内等待；别的进程用 Redis 锁）
        │ 4 自己算（检索，或整个 ask_docs 图）
        │ 5 结果完整就写缓存（过期 1 小时；「没找到」10 分钟）
        └ 6 影子模式：只对 search_docs，记下语义缓存会怎么做
```

键里的字段（每个字段改了键就变，各有一个测试）：

| 字段 | 为什么要有 |
|---|---|
| 接口（search 或 ask）、知识库、索引前缀 | 不同接口、不同库的结果不同 |
| 数据代号 | 数据变了（摄取、换索引）旧结果不能再用；增量摄取不改索引版本，只靠它 |
| 检索配置版本 | 知识库配置、向量模型、重排模型一变，结果就变 |
| 回答配置版本（只有 ask） | 知识库的 `agent` 和 `answer` 配置、聊天模型、`agent_*` 设置、各步骤提示词的文字 |
| 规范化的问题 | 只去掉大小写、多余空白和句尾的 `? ! .`；问题里有标识符（`LoRA`、`push_to_hub`、版本号、参数名、路径、引号里的整句）时不转小写；不做词干还原 |
| 过滤条件 | 带 `doc_type` 过滤和不带的结果不同；值的列表当集合处理 |
| 权限组（排序去重后的集合） | 权限不同的人不能拿到对方的结果 |
| `top_k`、语言 | 它们决定返回几段、用什么语言写 |

存进 Redis 的值是一段 JSON：版本、接口、`created_at`、全部键字段（调试用），再加结果本身。结果里没有请求编号、会话编号、各路检索各自的列表、重排列表、首次运行的耗时和 token 数。不压缩；超过 256 KB 不存。

### 1.4 哪些结果不写缓存

每条规则一个测试。

| 不写的情况 | 原因 |
|---|---|
| `degraded`（只有一路检索答了） | 网关故障时只有 BM25 的结果会在过期前一直返回 |
| `rerank_timeout`（重排超时） | 同上，排序不完整 |
| `answer_parse_failed`、任何模型错误类别 | 没有回答，只有检索到的段 |
| `coverage_unconfirmed`（没确认是否查全）、撞到时间或 token 上限 | 回答只用了运行停止前查到的段 |
| 要用户澄清、澄清之后继续的运行 | 结果取决于用户的回复 |
| 用了对话历史、`cache_allowed=false` | 追问脱离上一轮看不懂 |
| 有步骤退回到规则或原问题（`fallbacks`） | 不是正常运行的结果 |

写的：完整的「没找到」。检索的「没找到」是索引对这个问题的真实回答；回答的「没找到」是干净运行的结果；两者过期更早（10 分钟）。

`ask_docs` 的两个特殊情况：带 `session_id` 的调用不读缓存（命中会跳过「把这一轮写进会话历史」），但没有历史时可以写，给后面没带会话的相同问题用；带 `resume_token` 的调用完全不进缓存。

真实调用里出现过这条规则起作用的例子（1.7.4）：机器忙时 5 个问题里 2 个第一次带了 `rerank_timeout` 或 `degraded`，它们没有写缓存，第二次问同一个问题时重新计算了。

### 1.5 Redis 出问题时

请求不会失败。连接和每条命令的超时是 50 毫秒；慢于这个，或者连不上，请求照常计算，响应里 `cache.outcome` 是 `error`，指标 `rag.cache.requests` 记一次，span 上有原因。连续 5 次失败以后 5 秒内不再发命令（`bypass`，原因 `breaker_open`），之后放一个请求试探，成功就恢复。读不到数据代号时也不用缓存，因为没有安全的键。

验证：单元测试用一个会抛错的内存存储；另有测试把客户端指向没人监听的端口（`redis://127.0.0.1:1`），没有停共享的 Redis 容器。真实服务的量法见 1.7.5。

同一个请求同时来很多个时只算一次：单元测试用 12 个线程（经 `search_docs`）、20 个线程、20 个和 10 个异步任务（经 `ask_docs`）同时问同一个问题，检索器或图都只被调用 1 次；用两个缓存对象共用一个存储模拟两个进程，也只算 1 次。第一个请求失败或被取消时，一个等待的请求接手，其余继续等它，错误不会传给别的请求。

另有 100 对正例（每类 20 对）：同一个问题两次、多余空白、句尾标点（含全角 `？`）、大小写（只对没有标识符的问题）、看不见的零宽字符。

每个问题最多出 3 个文字类反例，因为同一个问题的几个反例互相关联，多了只会让区间看起来比实际窄。

**人工检查**：按固定规则抽 40 对（`review_sample`，每类取几对），逐对读：38 对是有效的反例或正例；2 对是 `identifier_case`（`CSPResNeXt` 写成 `cSPResNeXt`），它们其实更像同一个问题的笔误，只是 L1 规定标识符区分大小写，所以不共用。我把这一类标成「规定类」，在 L2 的主数字里不算。

**L1 的结果**：474 对反例里，L1 误命中 0 对；100 对正例全部共用一个条目。这是按构造成立的：键是规范化字段的哈希，每个反例至少有一个字段在规范化之后不同（一个词、一个标识符连大小写、一个数字、或者请求的其他条件），所以哈希不同。测试对每一对都检查一遍。设计 12.4 说「换专有名词」这类反例对规则本来就是 0，测了说明不了别的情况，所以这里的 0 只作为 L1 键写对了的证明，不作为语义缓存安全的证据。

### 1.7 测量

机器在测量时很忙（另一个子任务和重排模型同时在跑），所以耗时偏长；比值比绝对值可信。

#### 1.7.1 L1 命中率和省下的时间（`search_docs`，真实 ES 和重排模型）

模拟负载：400 个请求，问题集合是公开 65 题、合成 dev 99 题和 15 条口语改写，共 179 个问题。每个问题被问到的概率和它的名次成反比（Zipf，指数 1.0，名次由固定的随机种子决定），这是真实问题日志常见的样子：少数问题问得多，大量问题只问一次。其中 15% 的重复请求改了写法（大小写、空白、句尾标点），用来检查规范化在真实流量里管不管用。请求一个接一个地发，测的是延迟，不是吞吐。

| 项目 | 数值 |
|---|---|
| 请求数、不同的问题数 | 400、110 |
| 命中 | 290（72.5%）。重复请求能命中的上限就是 72.5%，实际达到了 |
| 改写过的重复请求 | 40 个，全部命中 |
| 命中耗时（中位数、第 95 百分位） | 10.1 毫秒、12.9 毫秒 |
| 未命中耗时（中位数、第 95 百分位） | 3,124 毫秒、5,301 毫秒 |
| 省下的时间 | 每次命中中位数 3,374 毫秒；总共 1,356 秒，不用缓存要 1,740 秒，实际用了 385 秒（省 78%） |
| 命中返回的第一段和这个问题第一次计算时一样 | 290 次里 290 次 |
| 花费 | 0.0002 元（只有没缓存过的问题向量） |

这个命中率完全由负载决定：重复的问题多就高，每个问题只问一次就是 0。真实流量里的重复程度还没有数据（见 1.9）。

#### 1.7.2 未命中时多付多少

每次未命中多做：读数据代号、读缓存、取锁、写缓存、放锁、算键，一共 6 到 7 次很小的操作。

| 操作 | 中位数 | 第 95 百分位 |
|---|---|---|
| 算键（含规范化） | 0.21 毫秒 | 0.30 毫秒 |
| Redis 读数据代号 | 1.37 毫秒 | 1.96 毫秒 |
| Redis 读（没有这个键） | 1.22 毫秒 | 1.97 毫秒 |
| Redis 读（6 KB 的值） | 1.25 毫秒 | 1.74 毫秒 |
| Redis 写（6 KB 的值） | 1.44 毫秒 | 2.00 毫秒 |
| 模拟负载里每次未命中的查找时间 | 3.6 毫秒 | 5.0 毫秒 |
| 模拟负载里每次未命中的写入时间 | 2.5 毫秒 | 4.0 毫秒 |

模拟负载里查找加写入约 6 毫秒，占未命中耗时（3.1 秒）的 0.2%。Redis 单次最长 12.6 毫秒，没有碰到 50 毫秒的超时。

#### 1.7.3 语义缓存的存储：内存和 ES 比较

2000 条 1024 维的问题向量，查最近的 3 条（带分区过滤）：

| 存储 | 查一次（中位数、第 95 百分位） | 写一条 |
|---|---|---|
| 进程内存（numpy 矩阵） | 0.51 毫秒、0.68 毫秒 | 微秒级 |
| ES 索引 `cache_semantic_<知识库>`（`flat` 向量索引） | 8.7 毫秒、11.2 毫秒 | 38 毫秒（等刷新），不等刷新要少得多 |

两者对要几秒的未命中都可以忽略。默认用 ES：设计 12.1 写明用 ES，重启后数据还在，多个进程共享；代价是每次查询慢 8 毫秒左右，多一个要依赖的服务（ES 不可用时影子模式只写一条警告，不影响请求）。要用内存版，设 `CACHE_SEMANTIC_STORE=memory`。

| 问题 | 第一次 | 第二次 |

| 000 | 未命中，9,317 毫秒 | 命中，68 毫秒（省 1,319 个 token） |
| 001 | 未命中，13,721 毫秒，带 `rerank_timeout`，**没写缓存** | 未命中，11,852 毫秒，干净，写了缓存 |
| 002 | 未命中，6,093 毫秒 | 命中，20 毫秒 |

| 004 | 未命中，6,987 毫秒，带 `degraded`，**没写缓存** | 未命中，18,277 毫秒，干净，写了缓存 |

命中的 3 次里 `tokens_used` 是 0：这次请求没有调用模型。样本只有 5 个问题，只能说明机制管用，说不出命中率。

#### 1.7.5 Redis 连不上时（缓存指向一个没人监听的端口）

20 个不同的问题，真实服务：

| 情况 | 中位数 | 第 95 百分位 | 失败 |
|---|---|---|---|
| 不带缓存层 | 3,339 毫秒 | 3,977 毫秒 | 0 |
| 缓存指向关闭的端口 | 3,506 毫秒 | 5,394 毫秒 | 0 |

12 个请求的结果是 `error`，8 个是 `bypass`（熔断打开）。没有一个请求失败。两行的差别在机器负载的波动范围内，这次没有量到熔断带来的额外延迟；连接被拒绝是立刻返回的，不会等满 50 毫秒。Redis 是慢而不是不通时的行为只在单元测试里用假存储验证过，没有在真实服务上量。

### 1.8 语义缓存（L2）：影子模式的结果

#### 1.8.1 它是怎么判断的

`search_docs` 未命中、结果完整时：从 L0 缓存里取出这个问题刚算好的向量（不再调模型；取不到记一条 `no_vector`）；在存好的问题里找距离最近的 3 个，必须同一个知识库、过滤条件、权限组、检索配置版本、数据代号、`top_k` 和语言；距离不超过阈值，并且通过检查，才算「会命中」；然后写一行 JSON 记录，再把这个问题存起来。返回的结果不变，测试把开关两种情况的输出逐字节比较。

检查有两层：

| 检查 | 规则 | 来源 |
|---|---|---|
| 专有名词检查 | 标识符、大写开头的名字、数字（含数字词和中文数字）、否定词必须一致；标识符和名字比较时不分大小写；两个问题都没有专有名词时，距离要小一些（阈值乘 0.6） | 设计 12.3 |
| 词汇检查 | 去掉停用词后，两个问题的实词只差一两个词就拒绝 | 我加的，原因见下 |

#### 1.8.2 为什么多加了词汇检查

只用向量距离和专有名词检查，量出来是这样（dev 部分，194 对「文字类」反例，不含规定类；这些反例的两个问题只有问题文字不同）：

| 阈值（距离） | 只看距离：误命中 | 加专有名词检查：误命中 | 再加词汇检查：误命中 | 15 对真改写里：只看距离 / 专有名词检查 / 全部检查接受 |
|---|---|---|---|---|
| 0.02 | 50 | 10 | 0 | 0 / 0 / 0 |
| 0.04 | 68 | 16 | 0 | 0 / 0 / 0 |
| 0.06 | 84 | 25 | 0 | 3 / 2 / 1 |
| 0.08 | 92 | 30 | 1 | 5 / 3 / 2 |
| 0.10 | 98 | 32 | 1 | 10 / 8 / 7 |
| 0.14 | 112 | 38 | 2 | 13 / 9 / 8 |
| 0.20 | 128 | 45 | 5 | 13 / 10 / 9 |
| 0.30 | 157 | 51 | 11 | 15 / 11 / 10 |

问题出在「只换一个词」的反例：把 `push` 换成 `pull`、加一个 `not`，这类问题的向量几乎不动。dev 部分各类的向量距离中位数：否定 0.013、数字 0.017、版本 0.039、反义词 0.045、换标识符 0.289、换问法（`aspect_change`）0.275。**真正的改写（15 对）要到 0.10 以上才开始被接受，而反义词和否定的问题在 0.05 以内**，所以任何距离阈值都分不开两者；专有名词检查也看不见反义词（没有专有名词）。设计 12.3 自己写过这个规则排除不了所有错误，这里量出来是第一类就占了 dev 误命中的大部分。词汇检查按「只差一两个词」拒绝，不依赖我写的反义词表，但它是个粗规则，代价是只差一个同义词的真改写也被拒掉（所以接受的真改写变少了）。

#### 1.8.3 阈值怎么选，holdout 上的结果

选阈值的规则：在 dev 上，取「带全部检查时反例误命中为 0」的最大阈值，选出 **0.06**。在 holdout 上用同一个阈值算一次（这是 holdout 唯一一次被计算）：

| 文字类反例（不含规定类） | 对数 | 只看距离：误命中 | 加专有名词检查 | 再加词汇检查（Wilson 95% 区间） |
|---|---|---|---|---|
| dev | 194 | 84（43%） | 25（13%） | 0（0% 到 1.9%） |
| holdout | 100 | 34（34%） | 12（12%） | **0（0% 到 3.7%）** |

holdout 上各类：反义词 20 对里只看距离误命中 12 对，专有名词检查仍然放过这 12 对（没有专有名词），词汇检查拒绝了全部；否定 20 对里只看距离全部 20 对误命中，专有名词检查拒绝了全部；换标识符、换问法在 0.06 以内本来就没有。

**这个 0 要怎么读**：100 对里一个误命中，真实的错误率仍可能高达 3.7%，设计 12.4 说过要说「不超过 1%」需要约 300 个反例都没有错误，这里文字类只有 100 对（每个问题最多出 3 个，已经把关联的反例限制住了），所以不能说「不超过 1%」。另外，这些反例大多是我用规则做的「改一个词」，词汇检查拒绝它们有一部分是按构造成立的；真实用户的错误命中不一定是这种样子。

阈值 0.06 下接受的真改写只有 1/15。如果只要求误命中很少，缓存几乎不会命中。

#### 1.8.4 真实模拟负载里的影子记录

在 1.7.1 的 400 个请求里，110 个未命中的请求各产生一条影子记录（阈值用 0.20 记录，报告可以读成更小的阈值）：

| 项目 | 数值 |
|---|---|
| 有记录的请求 | 110（没有 `no_vector`） |
| 会命中 | 5（4.5%，Wilson 区间 2.0% 到 10.2%） |
| 其中错误（第一名的块不同） | 2 / 5（40%，区间 11.8% 到 76.9%）；有 gold 页的 5 个都核对了 |
| 检查拒绝的候选 | 4（标识符 2、名字 1、词汇 1） |
| 距离太远 | 100 |
| 查找耗时（内存存储）中位数、第 95 百分位 | 3.0 毫秒、4.1 毫秒 |
| 只读距离 0.10 以内时 | 会命中 3（2.7%），错误 0 / 3（区间 0% 到 56.1%） |

5 个会命中的全是口语改写对公开原题（模拟负载里有这 15 对）。这个负载里没有别的相近问题，所以会命中率很低，不能当成真实流量的会命中率。错误的 2 个是距离 0.109 和 0.116 的（`nystromformer` 和 `textual inversion` 的口语改写）：第一名的块和原题不同，前 10 个块的重合分别是 62.5% 和 87.5%。距离在 0.09 以内的 3 个第一名都和原题相同，但前 10 个块的重合只有 50% 到 100%（这些口语改写问的是同一件事，用词不同，检索出的块不完全一样）。

#### 1.8.5 什么时候可以打开 L2（规则）

设计 12.4 和 15.1 已经写了两条，我补了第三条的数字：

1. 影子记录里，错误命中率的 Wilson 区间上限不超过 1%（设计 15.1 的提醒线）。0 个错误至少要 380 个会命中的请求，上限才降到 1% 以下。
2. 至少 5% 的未命中请求会命中（我定的下限，低了不值得担风险；设计 12.4 说「命中率太低就不开」）。
3. 真实流量里抽查「会命中」的请求，前 10 段重合度也在可接受的范围。

`python -m rag.cache shadow-report` 按这个规则给出结论，现在的结论是「保持影子」。

### 1.9 没有覆盖、没有验证的

- **真实流量里的命中率**：1.7.1 的 72.5% 来自我设定的 Zipf 负载，不是真实日志；真实命中率取决于用户重复提问有多频繁。上线以后看 `rag.cache.requests` 的命中比例。
- **语义缓存的会命中率和错误率**：只有 400 个模拟负载请求的影子记录，会命中的 5 个太少，区间很宽；要在真实流量上积累以后再用 `shadow-report` 判断，现在不开。
- **词汇检查的泛化**：它在我用规则做的反例上拦得住，但这些反例大多是「改一个词」，是按构造能被它拒绝的样子；真实的相近问题（例如问同一个函数的不同方面、用词很不一样）没有样本。
- **MT5 手册**：MT5 的问题集只在本机，没有用；两个检查里的英文规则对中文问题只做了专有名词和否定词，词汇检查对中文不做。
- **`ask_docs` 的语义缓存**：没有做。设计 12.2 说语义缓存缓存的是检索结果，`ask_docs` 的图有多轮和改写，没有一个稳定的「这个问题的检索结果」。
- **Redis 慢（不是不通）时的真实服务行为**：只有假存储的单元测试和关闭端口的测量。
- **多进程**：用两个缓存对象共用一个存储，和真实 Redis 上两个线程模拟了两个进程；没有起两个服务进程实测。
- **数据代号读不到时（不是整个 Redis 不通）**：等价于上一条，不另外量。
- **缓存目前不删除旧条目**：靠过期和数据代号失效；ES 里的影子索引不会自动清理旧数据代号的条目，只有过期时间让它们不再被匹配（`python -m rag.cache drop` 只清 L1）。
- **响应里新增的 `cache` 字段**：HTTP、MCP 的输出结构多了一个字段（可为空）；没有查有没有外部调用方因为字段多了而出错，仓库内所有现有测试都没有改动就通过。
