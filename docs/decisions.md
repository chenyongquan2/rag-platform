### 2026-10-17 P0-01：只有 kb/public/ 下的知识库默认对所有调用方开放
评审指出：`access.callers` 默认 `["*"]` 的话，私有知识库的配置只要漏写 `access`，所有调用方都能查到。现在的规则：
- 判断是不是公开知识库，只看配置文件相对 kb 根目录的路径是否以 `public/` 开头；`kb/private/public/x.yaml` 算私有。
- `kb/public/` 下的配置没写 `access` 时，`callers` 取 `["*"]`，所有已认证的调用方都能用。公开知识库仍然只写数据源就能用，符合设计 5.1。
- 其他目录（比如 `kb/private/`）下的配置没写 `access` 时，`load_kb_config` 直接报错，错误信息里写明要设置 `access.callers`。
- 在代码里直接构造 `KnowledgeBaseConfig` 而不给 `access` 时，`callers` 是空列表，谁都不能访问。

评审给了两个做法：私有配置漏写时报错，或者默认空列表、谁都不能访问。选报错，原因：默认空列表时知识库照常加载，只是所有调用都查不到内容，主人要排查一阵才知道是漏写了 `access`；报错在服务启动时就把文件名和要补的字段说清楚。

### 2026-10-17 P0-03：HF 文档集下载 Hub 自动转换出来的 parquet，不下载原始 CSV
`m-ric/huggingface_doc` 的 main 分支里只有一个 `huggingface_doc.csv`（21,954,601 字节）。Hugging Face Hub 会自动把数据集转成 parquet，放在 `refs/convert/parquet` 分支（`default/train/0000.parquet`，10,058,873 字节）。选 parquet 的原因：
- 任务要求下载 parquet。
- parquet 带列类型，读的时候不用处理正文里大量的换行和引号转义；文件也小一半。
- 清单里写明下载哪个提交（`ec31afec…`），以后 Hub 重新转换出新的提交，也不影响我们下载的这一版。清单的 `note` 里记了它是从 main 的哪个提交（`1b83935…`）转出来的。

还考虑过：直接下载 CSV。好处是用户上传的原文件，不依赖 Hub 的转换。如果转换分支的这个提交以后被删掉，就改成下载 CSV，需要加一段读 CSV 的代码。评测题集 `m-ric/huggingface_doc_qa_eval` 的 main 分支本身就是 parquet，直接用 main 的提交 `5f70aa9…`。

### 2026-10-17 P0-03：自己用标准库下载，不用 huggingface_hub 的 hf_hub_download
下载地址按 Hub 的格式自己拼：`<endpoint>/datasets/<repo>/resolve/<提交 id>/<文件路径>`，用 Python 标准库 urllib 下载。文件存到 `<HF_DATA_DIR>/<repo>/<提交 id>/<文件路径>`。原因：
- huggingface_hub 的缓存目录用 blobs 加 snapshots 符号链接。Windows 上没有建符号链接的权限时，它会改成复制文件，目录结构和 Linux 上不一样。
- 它不会按我们的清单核对大小、sha256 和行数，这一步反正要自己写。
- 自己拼地址，单元测试可以把地址换成 `file://` 的本地目录，不联网就能测下载、缓存和核对。

还考虑过：用 huggingface_hub。它已经是间接依赖，也认 `HF_ENDPOINT` 环境变量。服务配置里新加的 `hf_endpoint` 字段读的也是 `HF_ENDPOINT`，两边设一次就都走镜像。

### 2026-10-17 P0-03：doc_id 写成「知识库名:相对路径」，HF 文档的相对路径就是 source 列
设计 5.4 要求 doc_id 由知识库、相对路径和单元组成。具体格式：`hf_docs:huggingface/transformers/blob/main/docs/source/en/bert.md`。文件里还分单元时（比如 CHM 里的页面），后面加 `#<单元>`。用冒号隔开知识库名，因为路径里本身有斜杠。路径里的反斜杠统一换成斜杠，绝对路径和带 `..` 的路径直接报错，这样同一个文件在 Windows 和 Linux 上得到同一个 id。

数据集的 `source` 列就是这篇文档在 GitHub 上的路径，所以 `source_url` 写成 `https://github.com/` 加上这个路径，前缀写在清单的 `doc_url_prefix` 里。实查 2,647 个 `source` 没有空值，也没有重复。以后出现重复时直接报错，不自动加序号：加序号的话，id 会随行的先后顺序变化，增量更新就认不出是同一篇。评测题的 `source_doc` 用同一个函数算 doc_id，65 题的来源文档都在文档集里。

### 2026-10-17 P0-03：limit 取文件里的前 N 行，不先按路径排序
知识库配置里的 `limit: 50` 取的是清单指定的那个 parquet 文件里的前 50 行。文件按 sha256 核对过，所以每次取到的 50 篇都一样。没有先按路径排序再取，因为按字母顺序排，前 50 篇全是 `gradio-app` 仓库的文档（共 469 篇，排在 `huggingface` 前面），而文件原来的顺序是各个仓库混在一起的。

### 2026-10-17 P0-03：清单里的大小、sha256 和行数由第一次下载记下，再提交
`data/manifests/hf_docs.json` 里的仓库、提交 id、许可、来源网址和预期行数（2,647 和 65）是手写的，大小、sha256 和每个文件的行数一开始留空。运行一次 `python -m rag.data.hf download --pin`，程序从下载下来的文件算出这三项写回清单。之后的下载和读取都要求这三项齐全，而且和文件一致。第一次记下的 sha256 和 Hub 接口返回的 LFS 对象 id（也是 sha256）比过，两个文件都一样。

下载先写到临时文件，核对通过才改名放进缓存，所以缓存里不会留下核对没通过的文件；两个 checkout 共用一个缓存目录、同时下载也不会读到写了一半的文件。`HF_DATA_DIR` 默认是 `data/raw/hf`（相对当前目录，在 .gitignore 里）。这次在 P0-03 的 worktree 里运行时，把它设成了 `C:\workspace\rag-platform\data\raw\hf`，主 checkout 以后用默认值就能直接用这份下载。

### 2026-10-17 P0-03 评审后：doc_id 的路径里的 # 和 % 改写成 %23 和 %25
doc_id 用 `#` 隔开文件路径和单元（比如 CHM 里的页面名）。如果文件名里本身有 `#`（比如 `c#.md`），读 doc_id 的程序就分不清哪个 `#` 是分隔符。现在 `make_doc_id` 把路径里的 `#` 写成 `%23`，`%` 写成 `%25`，单元里的 `#` 不改。这样路径之后的第一个 `#` 一定是分隔符，两个不同的路径也不会算出同一个 id。路径里的 `a//b`、`a/./b` 先合并成 `a/b`。

还考虑过：路径里有 `#` 就报错。缺点是以后接本地目录、PDF 时，文件名里有 `#` 的文档整份读不进来。HF 文档集的 2,647 个路径里没有 `#`、`%`、`//` 和 `/./`，改完以后它们的 doc_id 和改之前一样（实查过）。

### 2026-10-17 P0-03 评审后：提交在仓库里的清单，相对路径从仓库根目录算
知识库配置里写的 `manifest: data/manifests/hf_docs.json`、`load_eval_questions` 收到的相对路径、命令行 `--manifest` 的默认值，都从仓库根目录算（`rag.config.repo_path`），不从当前目录算。原因：清单是提交在仓库里的文件，在别的目录下运行程序也应该找到同一份。命令行里明确传的 `--manifest` 还是按当前目录算，和一般命令行工具一样。

P0-01 定的规则（连接串里的相对路径从当前目录算）不变：`data/docstore`、`HF_DATA_DIR` 这些是运行时写出的数据，不是仓库里的文件。

### 2026-10-17 P0-02：本机端口都用「标准端口加 20000」，只绑 127.0.0.1
- 这台机器上 6379、4317、4318、13133、16686 已经被别的项目的容器（还有一个本机的 Redis 进程）占着。停掉别人的容器会影响别的项目，所以不用这些端口。
- 这台机器的 Windows 动态端口范围是 1024 到 15000（Windows 默认从 49152 开始），Hyper-V 会在这个范围里成段保留端口；当时 6380 到 6479 被保留，compose 绑 6380 直接失败。保留哪几段在重启后会变，所以端口全部放在 15000 以上：ES 29200、Redis 26379、OTLP gRPC 24317、OTLP HTTP 24318、Collector 健康检查 33133、Jaeger 页面 36686。
- `ServiceSettings` 的默认连接串跟着改，而且写 127.0.0.1 不写 localhost。实测 Python 连 localhost 每次多等约 2 秒（先试 IPv6 的 ::1，被拒绝后才试 127.0.0.1），连 127.0.0.1 约 10 毫秒。P0-01 的默认值测试 `test_service_settings_defaults` 因此改了。
- 还考虑过：在 compose 里用环境变量配端口。换一台机器端口冲突时更方便，但现在只有这一台开发机，先不加。

### 2026-10-17 P0-02：索引映射按 ES 9.5.5 实测确认，另外多写了三项
- 9.5.5 接受设计 7.3 的写法：`int8_hnsw` 加 `rescore_vector.oversample=3`，取回的映射和写进去的一样。
- HNSW 的 `m=16`、`ef_construction=100` 是 ES 现在的默认值，也写进映射，以后升级时默认值变了，已有配置不跟着变。
- 9.5 新建的索引默认 `index.mapping.exclude_source_vectors=true`，查询结果的 `_source` 里不带向量。映射里显式写成 true：检索用不到向量原文，返回的数据少很多。以后要从 ES 取回向量时，在查询里单独要。
- `dynamic: strict`：写入映射里没有的字段时 ES 直接报错，不自己猜类型。比如把 `acl_groups` 拼错，写入时就会失败；如果让 ES 自动加字段，权限过滤会一直匹配不到，却没有任何报错。P0-06 写入时要多存字段，先在 `rag.index.mapping` 里加上。还考虑过 `dynamic: false`（映射里没有的字段只存进 `_source`、不建索引）：写入不报错，拼错的字段名要等查询结果不对才发现。
- 向量类型做成 `VectorIndexOptions`，可以选 int8_hnsw、bbq_hnsw、flat 等，留给 P2 做消融；bbq_disk 要 Enterprise 许可证，不提供。

### 2026-10-17 P0-02：数据代号存在会淘汰键的 Redis 里，键丢了就从当前毫秒时间重新开始
- 问题：redis-cache 按计划配置成 allkeys-lru，也不存盘。数据代号这个键可能被淘汰，Redis 重启后也会丢。如果丢了以后从 0 或 1 重新数，就会回到以前用过的值，用这个旧值做键的缓存会再次被命中，返回已经改过或删掉的内容。
- 做法：键不存在时先写入 Redis 服务器当前 Unix 时间的毫秒数，再读或加 1。判断键在不在、读服务器时间（`TIME`）、写入、加 1 放在同一个 Lua 脚本里，Redis 执行脚本时不会插进别的命令。这样新值一定比以前所有的值大，前提有两个：一个知识库加 1 的次数少于这段时间经过的毫秒数（每次摄取至少几秒，实际一定满足）；Redis 服务器的时钟没有往回调。读的时候键不存在也会写入，保证连续几次读到同一个值。
- 评审后改成用 Redis 服务器的时钟，不用调用方本机的时钟：几个进程可能跑在时钟不一致的机器上，某台机器的时钟慢了，它重新写入的值就可能比以前用过的值小。所有进程连的是同一个 Redis，用它的时钟就只有一个时钟。
- 代价：数据代号是 13 位的大数，不是 1、2、3 这样的小数。
- 还考虑过：改成 volatile-lru，只淘汰设了过期时间的键，数据代号不设过期时间就不会被淘汰；但这要求所有缓存键都设过期时间，而且和计划里写的 allkeys-lru 不一致。另起一个不淘汰键的 Redis 专门存数据代号，要多一个容器。存在 ES 索引的 `_meta` 里，每次查缓存都要先多查一次 ES。

### 2026-10-17 P0-02：切换别名和删除旧索引怎么防出错
- `switch_alias` 在一个 `_aliases` 请求里同时做「从旧索引去掉别名」和「给新索引加上别名」，ES 对这个请求要么全部执行、要么全部不执行。集成测试里两个线程不停地按别名查询，主线程同时来回切换 20 次，每次查询都只看到一个索引，没有出现查不到或者两个索引都查到的情况。
- 调用方可以传 `expected_current`，表示「我确认过别名现在指向 v1」。去掉 v1 上的别名时带 `must_exist`，如果别名已经被别人切走，ES 拒绝整个请求，别名保持原样。
- 评审发现的问题：调用方以为别名已经在目标索引上（`expected_current` 等于要切到的索引）时，原来的代码省掉了带 `must_exist` 的那一步，请求只剩「加别名」。如果别名其实已经被切到别的索引，加完以后别名同时指向两个索引，查询会查到两份结果。现在无论是否等于目标，都先带 `must_exist` 去掉预期索引上的别名，再加到目标上；ES 允许同一个请求里对同一个索引先去掉再加回。
- ES 拒绝请求时按错误类型区分：别名不在预期索引上（`aliases_not_found_exception`）、预期索引已经不存在，都报「别名被别人改过」；要切到的索引在检查之后被删了，报索引状态错误；其他错误原样抛出，不当成别名冲突。
- 两个进程同时切换同一个知识库的别名，要靠摄取锁防止（P0-06），这个函数自己不加锁。
- `delete_kb_index` 只接受本知识库带版本号的完整索引名，别名、通配符、别的知识库的索引都不删；索引上还挂着任何别名时也不删，要先把别名切走。检查和删除是两次请求，中间被切换的情况同样靠摄取锁防止。
- 命令行的 `switch` 先切别名，再把数据代号加 1。顺序反过来的话，加 1 之后、切换之前写进的缓存会带着新代号，内容却是旧索引的。如果切完别名时 Redis 连不上，命令报错并提示重跑同一条 `switch` 命令：重跑时别名已经指向目标，不再变动，只把数据代号加 1。

### 2026-10-17 P0-05：网关一次最多收 10 条文本，默认每批 10 条；超时、重试和等待上限按用途分开
探测方法：不重试，向网关依次发 1 条、10 条、11 条很短的文本（`t0`、`t1`……）。10 条成功；11 条返回 HTTP 400，错误信息是 batch size 不能大于 10。所以 `embed_batch_size` 默认 10。配置允许的上限 2048 是 LlamaIndex 自己的上限，设成大于 10 时网关返回 400，第一次请求就报错，不会重试。

同时量到：单条文本一次请求约 0.6 秒，第一次 1.75 秒（包括建立 TLS 连接）；10 条一次请求 2.6 秒（也是新连接）。同一段文本连发三次，三个向量逐位相同。

超时和重试（评审后改过，见表后）：

| 用途 | 单次超时 | 最多重试 | 两次之间等多久 | 最多等多久 | 总时限 | 网关一直不通时最坏等多久 |
|---|---|---|---|---|---|---|
| 摄取 `ingest` | 60 秒 | 4 次 | 2、4、8、16 秒 | 60 秒 | 不限 | 每批约 330 秒 |
| 查询 `query` | 3 秒 | 1 次（配置不允许大于 1） | 0.2 秒 | 1 秒 | 7 秒 | 约 6.2 秒 |

会重试的错误：超时、连接失败、HTTP 408、429 和 5xx。网关带了 `Retry-After`（秒数）时按它等；它要求等的时间超过这个用途的「最多等多久」，程序不等，直接抛 `EmbeddingError`。查询还有总时限：每次请求的超时取「单次超时」和「离总时限还剩的时间」中小的那个；如果等完再试会超过总时限，也直接报错，不再等。其他错误第一次就报错：400、401、403、404 等 4xx，回答不是 JSON，向量条数不对，维度不对。直接写 `text-embedding-v4` 时网关一直返回 503，会按 5xx 重试到次数用完再报错，摄取时要多等约半分钟才看到错误；没有为它单独处理。

评审后改的：第一版两种用途共用一个 30 秒的等待上限，查询碰到一次带 `Retry-After: 30` 的 429，就要等 30 秒，和设计 16.2「查询用短超时」矛盾。现在每种用途有自己的上限，查询另有 7 秒的总时限。`Retry-After` 超过上限时直接报错，不改成少等几秒再试：网关要求等 30 秒，等 1 秒再试多半还是 429，只是多发一次请求。

### 2026-10-17 P0-05：L0 缓存的键里加上维度和文本前缀，向量按 float32 存
设计 12.1 写的键是「向量模型名 + 文本哈希」。实际的键分两部分：模型部分是 `qwen/text-embedding-v4@1024`，配了文本前缀时再加前缀的 sha256 前 12 位；文本部分是原文的 sha256。原因：同一个模型名，换了维度（text-embedding-v4 支持 64 到 2048 维）或换了前缀，同一段文本的向量就不一样了。只用模型名做键，改了维度以后，缓存会返回旧维度的向量。

- 向量按 float32 存，1024 维占 4 KB。ES 的 dense_vector 本来就按 float32 存。网关新返回的向量也先转成 float32 再交给调用方，所以同一段文本不管是不是从缓存读的，拿到的数字都一样。
- 同一批里重复的文本只发一次。查询和摄取用同样的键：两边前缀相同，同一段文本的向量相同（llm 测试实测逐位相同）。
- 摄取用 SQLite 文件 `data/cache/embeddings.sqlite3`（`data/cache/` 已在 .gitignore 里），WAL 模式。每次请求拿到的向量用一个事务写进文件，再发下一次请求，所以摄取中途停下，重跑时只算还没写进缓存的文本。

还考虑过：用 LlamaIndex `BaseEmbedding` 自带的 `embeddings_cache`。它的键是原文本身，不带模型名；一条一条读写，一批 10 条要读写 10 次；存的值是「随机 uuid 对应向量」，以后的版本可能改格式。所以自己写了 `CachedEmbedding`，包在客户端外面，一批只读一次、写一次。

### 2026-10-17 P0-05：查询缓存默认用 redis_url，Redis 出错时当作没命中
`embed_query_cache_url` 留空时用 `redis_url`，因为设计 16.7 规定缓存只用一个 Redis；单元测试或者本机没开 Redis 时可以设成 `memory://`。键是 `rag:l0:<模型部分>:<sha256>`，30 天过期。compose 里的 Redis 设了 allkeys-lru，内存满了会删掉最久没用的键。

Redis 连不上或读写报错时，程序记一条警告，当作没命中，查询照样去网关算向量；连接和读写的超时都是 0.5 秒。原因：缓存只用来省钱、省时间，Redis 出故障不该让查询失败。

没有用 P0-02 写的 `make_redis_client`：它设了 `decode_responses=True`，Redis 返回的值会被当成文本解码，二进制的向量会解码失败。所以缓存自己用 `Redis.from_url` 建客户端，不解码。

### 2026-10-17 P0-05：账本记哪些请求；发请求之前先预留预算，同时最多 4 个请求
网关每返回一次 2xx，账本就加一行。token 数从响应的 usage 读；没有 usage，或者回答解析失败时，按字符数估算，这一行写 `usage_estimated: true`。请求发出去以后读超时或者连接断开（httpx 的 `ReadTimeout`、`ReadError`），网关可能已经算完并扣了费，也按字符数估算记一行，并写上 `error` 字段（评审后加的）。连不上、4xx 和 5xx 不记，因为网关没有处理这个请求（我的推断，没查到网关的计费说明）。

并发和预算（评审后改的）：评审实测 `IngestionPipeline.arun` 把所有批次同时发出去，一次有 20 个请求在等网关；第一版每个请求各自查一次预算，大家都看到「还没超」，就一起发出去，合起来可能超过 28 元。现在：

- 每个客户端同时最多 `embed_max_concurrency`（默认 4）个请求在等网关，其余的在线程里排队。
- 每个请求发出之前，先用 `CostLedger.reserve` 预留这次请求的估算金额（把字符数当 token 数，比实际多）。查和占在同一把锁里做：读账本里已经花的钱，加上正在进行的请求预留的金额，再加这次的估算，超过 `budget_stop_cny`（28 元）就抛 `BudgetExceeded`，不发请求；不超过就记下预留的金额。请求结束以后删掉这笔预留。同一进程里写同一个账本文件的 `CostLedger` 对象共用这份记录，`check_budget` 也把它算进去。
- 不同进程之间看不到对方预留的金额。几个进程同时调真实模型时，最多多花各自正在进行的那几个请求的钱：一个请求 10 块、每块 2,000 字符时估算约 0.01 元，每个进程最多 4 个，离 30 元的总预算还差 2 元，够用。

每次查预算都读整个账本：HF 文档全量摄取约 500 万 token，按每块约 400 token、每次 10 块估算，约 1,250 次请求，账本也只有一千多行；用 1,250 行的账本实测，查一次预算约 13 毫秒，比一次请求的两秒多小得多。以后行数多到拖慢请求，再改成把总数存在内存里。

每行的字段：time、kind、model、prompt_tokens、completion_tokens、total_tokens、cny，再加调用方自己的字段（profile、inputs、usage_estimated、error）。写的时候加文件锁，几个进程同时写，两行也不会混在一起。最后一行如果因为进程崩溃只写了一半，读的时候跳过并记一条警告。

### 2026-10-17 P1-01：对话模型的重试和账本记录都放在 httpx 传输层，不用 LangChain 回调
`make_chat_model` 用 `init_chat_model` 建 `ChatOpenAI`，同时传进去两个自己建的 httpx 客户端（同步、异步各一个），客户端的传输层是 `LedgerTransport` 和 `AsyncLedgerTransport`。传输层是 httpx 客户端里真正把请求发到网络上的那个对象，客户端每发一次请求都调用它一次。openai SDK 自己的重试关掉（`max_retries=0`），所以 SDK 发一次请求就是一次调用，重试由传输层做（评审后改的，原因见下一条「三套配置」）。传输层对每次尝试做这几件事：

- 发出之前，按请求估算金额，用 P0-05 的 `CostLedger.reserve` 预留。已花的、正在进行的请求预留的、这次估算的三项加起来超过 `budget_stop_cny`（28 元），就抛 `BudgetExceeded`，请求不发出去。估算是上限：请求体的字符数当输入 token 数，请求里的 `max_completion_tokens` 乘以要几个回答（`n`，默认 1）当输出 token 数。所以 `max_tokens` 越大，每次预留越多：online 配置的 4096 个 token 按估计价约 0.033 元。
- 网关返回 2xx 以后，从响应的 usage 读 token 数，账本加一行；流式请求读最后一个事件里的 usage。读超时、连接中途断开、流式回答没读完就被关掉（用户关了页面），网关可能已经生成并扣了费，按估算记一行，带 `error` 字段。连不上、4xx 和 5xx 不记，和 P0-05 一样。服务器一个字节的回答都没发就关了连接，也不记（见下一条「重试哪些失败」）。
- 调用在请求交给网络以后被取消，也按估算记一行（评审后加的，第一版只删掉预留、不写账本）。取消有两种：异步调用外面套了 `asyncio.wait_for` 之类的时限，到时抛 `CancelledError`；同步调用时按了 Ctrl+C，抛 `KeyboardInterrupt`。传输层看不出取消的那一刻请求有没有发出去，一律当作发出去了：账本里可能多出一行网关没扣费的估算，但预算检查不会少算。
- 每行除了 P0-05 的字段，还有 `profile`、`reasoning_tokens`、`stream`、`served_model`（网关实际用的模型，现在是 deepseek-v4.1-flash）、`price_estimated`。
- 网关的错误回答里如果原样带出了 API key，传输层先把它换成 `***`，再交给 SDK 拼进异常信息。

按五条标准比了三种做法：

| 做法 | 每次尝试都预留、都在账本里写一行；能给一次调用设总时限 | invoke、stream、结构化输出、同步异步都覆盖 | 能读到推理 token | 代码量 | 换成非 OpenAI 格式的接口 |
|---|---|---|---|---|---|
| LangChain 回调：开始时预留，结束时在账本里写一行 | 不能 | 能，但回调里抛的异常默认只写日志、请求照发，要设 `raise_error=True` | 能 | 约 100 行 | 能用 |
| 继承 `ChatOpenAI`，改写 `_generate`、`_stream` 等四个方法 | 能，但重试要在四个方法里各写一遍 | 能 | 能 | 约 250 行 | 不能用，也不能再用 `init_chat_model` |
| httpx 传输层（选这个） | 能 | 能，不依赖 LangChain 内部怎么调 | 能，直接读网关返回的 usage | 约 400 行，要自己解析流式回答的 SSE 事件 | 要改这一层 |

- SSE（Server-Sent Events，服务器推送事件）：服务器在一个 HTTP 连接里一段一段地往客户端发数据，每段是一行 `data: {...}`；OpenAI 格式的流式回答就是这样发的，最后一段带 usage。
- 回调看不到重试：第一次请求读超时、再发一次，回调只收到最后一次的结果。第一次如果已经被网关计费，账本里就少一笔。P0-05 定过「读超时也记一行」，只有传输层能做到。
- 第一版让 SDK 重试，传输层只往账本里写记录。评审要求给在线调用设总时限，可是 SDK 发的请求里没有「这几次尝试属于同一次调用」的编号，传输层分不出哪几次尝试是同一次调用，没法算总时限；SDK 还会重试读超时。所以把重试挪进传输层，SDK 不再重试。
- 代价：这一层依赖 OpenAI 的响应格式（usage 字段、SSE 的 `data:` 行），重试也要自己维护（和 P0-05 的向量客户端是两份相似的代码）。换成别的格式的接口时，要改这一层。
- 外层客户端换了传输层以后，httpx 不再读环境变量里的代理设置。这台机器设了 `HTTPS_PROXY`，所以传输层里面再用一个普通的 `httpx.Client` 发请求，代理和 `NO_PROXY` 照样生效，和向量客户端一致。每次尝试用 SDK 设在请求上的超时，按总时限截短。
- 我们自己传了 httpx 客户端，langchain-openai 不会再往客户端里加 TCP 选项；工厂另外传 `http_socket_options=()`，免得它打印「代理自动检测被关掉」的警告（评审后加的）。
- 网关压缩过的回答，传输层先解压再交给 SDK，否则读不到 usage。

### 2026-10-17 P1-01：结构化输出默认 function_calling，实测网关不支持 json_schema
实测方法：cheap 配置，同一个问题（「7 是质数」这句话对不对），Pydantic 类 `Verdict` 有 `is_true` 和 `reason` 两个字段，两种方式各调一次。

| 方式 | 结果 | 耗时 |
|---|---|---|
| `function_calling` | 返回正确的 `Verdict` | 1.5 秒 |
| `json_schema` | 网关返回 HTTP 400：`This response_format type is unavailable now`；账本里没有写这一次 | 0.3 秒 |

所以 `chat_structured_output_method` 默认 `function_calling`，和设计 11.1 一致。`ChatOpenAI` 用 `function_calling` 时，请求里只放这一个工具，并用 `tool_choice` 指定模型必须调用它；deepseek-v4.1-flash 是推理模型，实测也接受指定的 `tool_choice`。这次调用输入 325 个 token（工具的 JSON Schema 占了大部分），输出 76 个，其中推理 11 个。配置里还允许 `json_schema` 和 `json_mode`，换成支持它们的网关或模型时可以改；`json_mode` 这次没有测。

`structured_output(model, schema)` 包了一层：模型没有调用工具时，LangChain 返回 None；参数不符合 Pydantic 类时，LangChain 把错误放在结果里。这两种情况都改成抛 `StructuredOutputError`（类别 `structured_output_failed`）。不让 None 往下传：路由节点拿到 None，不知道该走哪条路，错误会在后面的节点才暴露。`FakeChatModel` 只模拟 `function_calling`。

### 2026-10-17 P1-01：三套配置的超时、重试和输出上限；推理 token 的实测
评审后改过，第一版的取值和改的原因见表后。

| 配置 | 用在哪 | 连接超时 | 读超时 | 总时限 | 最多重试 | 两次之间等多久 | `max_tokens` |
|---|---|---|---|---|---|---|---|
| `online` | 写回答 | 3 秒 | 10 秒 | 12 秒 | 1 次 | 0.5 秒，最多 1 秒 | 4096 |
| `cheap` | 改写、路由、判断够不够 | 3 秒 | 8 秒 | 10 秒 | 1 次 | 0.5 秒，最多 1 秒 | 1024 |
| `offline` | 出题、裁判 | 10 秒 | 180 秒 | 不限 | 4 次 | 2、4、8、16 秒，最多 60 秒 | 8192 |

三套配置默认都用 `chat_model`（deepseek-v4-flash），`temperature` 都是 0。每套是环境变量里的一个 JSON，只写要改的键，其余用这套配置的默认值，例如 `CHAT_ONLINE='{"read_timeout_s": 8}'`。

几个时间的意思：

- 连接超时：和网关建立连接最多等多久。
- 读超时：最多等多久收不到新数据。不流式调用时，网关生成完才返回，读超时就是整个生成最多花多久；流式调用时，是两段数据之间最多隔多久。推理内容也是一段一段发的，正常生成时两段之间远不到 1 秒。
- 总时限：一次调用的所有尝试和等待加起来，到回答开始返回为止，不能超过它。每次尝试的超时截到剩下的时间；再等一次就会到总时限时，不再重试。网关一直不回应时，online 调用 12 秒内、cheap 调用 10 秒内一定报错。流式回答开始返回以后，总时限不再管它，只受这次尝试的读超时限制，也就是两段数据之间最多隔多久，正常生成的长回答不会被切断。如果这次尝试是重试，它的读超时已经按开始时剩下的时间截短过，比如 online 第二次尝试在第 4 秒开始，两段数据之间最多隔 8 秒。offline 不设总时限，最坏约 4 分钟：前 4 次连接超时加等待约 70 秒，第 5 次连上以后读超时 180 秒。

重试哪些失败：

- 重试网关还没收到完整请求的失败（连不上、连接超时、请求没写完），以及 408、429 和 5xx 回答。
- 等回答时读超时不重试。不流式时，这就是整个回答没在读超时之内生成完；流式时，是第一段数据迟迟没来。请求已经发出去，网关可能还在生成第一个回答，并且会扣费；再发一次要付两份钱，第二次多半也一样慢。第一版交给 SDK 重试，SDK 会重试这种读超时，这是评审后改的。
- 流式回答开始返回以后，中途读超时或者连接断了，本来就不会重试，第一版也一样：SDK 和传输层都只能重新发还没开始返回的请求，前半段回答已经交给调用方了。这种情况按估算记一行。
- 服务器一个字节的回答都没发就关了连接（httpx 报 `RemoteProtocolError`），当作网关没收到请求：重试，账本里不写这一次。常见原因是连接池里留着的连接已经被服务器关掉了（评审第二轮后加的）。我的推断：网关在生成过程中崩溃也可能这样断开，那时账本会少记一次，这种情况很少见。
- 网关在 `Retry-After` 里要求等的时间超过「最多等多久」，直接报错，不等。和 P0-05 一样：网关要求 online 调用等 30 秒，就直接失败。

第一版的取值和为什么改：第一版每套配置只有一个超时，online 30 秒、cheap 20 秒、offline 180 秒，重试交给 SDK。网关接受连接但一直不回应时，online 调用要等两次 30 秒加 0.5 秒，约 61 秒。评审指出：设计 11.1 写的是在线回答「几秒超时」，16.8 要求不让调用方一直等，而且 61 秒比常见 MCP 客户端的 60 秒超时还长，MCP 客户端会先放弃。现在 online 最坏 12 秒。

代价和条件：

- 不流式调用时，生成超过 10 秒的回答会读超时失败。实测短回答 1 秒多，流式时第一段正文 1 秒左右到；按每秒约 50 个 token 算（我的推断，这次没有测几百个 token 的长回答），10 秒能生成约 500 个 token（推理加正文），够一个几句话的回答。问答页面用流式，不受这个限制。P1-02 和 P1-04 会实测几十个真实回答的耗时，长回答经常超过 10 秒的话，就加大 online 的读超时和总时限，或者让 MCP 工具也用流式调用。
- cheap 的 `max_tokens` 从 2048 改成 1024：它只输出一个小 JSON，实测结构化输出一共 76 个 token，其中推理 11 个。1024 给推理留够，每次预留的金额也从约 0.016 元降到约 0.008 元。

2026-10-17 实测四次调用（`tests/llm/test_chat_gateway.py`，每次输出上限 1024 个 token）：

- online 配置问「法国首都是哪」，要求只答一个词：1.5 秒返回 Paris。输入 42 个 token，输出 19 个，其中推理 17 个。
- 流式让模型从 1 数到 10：收到 15 个分块，4 个带正文，其余是推理内容、结束标记和 usage。第一个带正文的分块 0.8 秒到，全部收完 0.84 秒。账本里这一行的 usage 来自最后一个事件，不是估算。以后问答页面用 SSE 边生成边显示时，可以直接用 `.stream()`。
- 推理 token 已经算在 `completion_tokens` 里：`total_tokens` 等于输入加 `completion_tokens`，网关另在 `completion_tokens_details.reasoning_tokens` 里给出推理 token 数，LangChain 放进 `usage_metadata.output_token_details.reasoning`。账本按 `completion_tokens` 算钱，另记 `reasoning_tokens`。如果别的网关的 `total_tokens` 显示推理 token 没算进 `completion_tokens`，程序把它加上再算钱。网关返回的推理文字（`reasoning_content`）`ChatOpenAI` 不保留，我们只需要 token 数，不需要推理文字。
- cheap 配置把 `max_tokens` 改成 16，让模型列出前 20 个质数：16 个 token 全部用在推理上，正文是空的，`finish_reason` 是 `length`。这说明两件事：网关遵守 `ChatOpenAI` 发的 `max_completion_tokens`，所以预留时把它当输出上限是对的；`max_tokens` 必须给推理留够。

评审后改完传输层，又跑了一次回答和流式这两个探测：回答 1.0 秒；流式 14 个分块，第一段正文 1.1 秒到，全部收完 1.3 秒；两次的 usage 都从网关读到，不是估算。

### 2026-10-17 P1-01 评审后：预算检查不再每次读整个账本
P0-05 的 `total_spent` 每次读整个账本文件，`reserve` 在一把全进程共用的锁里调用它。对话模型的异步调用在事件循环里做这一步：账本到一千多行时每次约 13 毫秒，这段时间事件循环处理不了别的请求，别的请求的预留也在等这把锁（评审指出）。

现在每个进程按账本文件记两样东西：已经读到文件的哪个位置，读过的部分一共多少钱。每次查预算只读文件里新加的部分，本进程和别的进程写的都算。最后一行还没写完（没有换行）先不算，下次写完再算。文件变得比读到的位置短（被改写，不是追加），从头重读。

还考虑过：用 `asyncio.to_thread` 放到线程里读。事件循环不再等，但每次还是读整个文件，等锁的问题也还在。

代价：有人在原处改了账本里已经读过的内容、而文件长度没变，正在运行的进程看不到这个改动，要重启进程。账本只追加，不应该手改。

### 2026-10-17 P1-01：网关不可用或预算用完时，手动设 CHAT_BACKEND=fake，程序不自动切换
设 `CHAT_BACKEND=fake` 以后，三套配置都返回 `FakeChatModel`，每次都回答 `chat_fake_reply` 这句固定的话（默认 `[fake chat model] no answer`）：不发请求，不写账本，也不检查网关地址和价格。假模型上的结构化输出拿不到对象（固定回答里没有工具调用），会抛 `StructuredOutputError`。`FakeChatModel` 为此加了 `default_response`：脚本里的回答用完以后用它，不设时仍然报错。

和 P0-05 的向量一样，不做「网关出错就自动换成假模型」：自动换了以后，评测分数和返回给用户的回答里会混进假回答，程序却不报错。网关出错时按设计 16.8 报 `llm_timeout` 或 `llm_error`，由调用方决定只返回检索到的段。预算用完时 `BudgetExceeded` 的错误信息里提示设 `EMBED_BACKEND=fake` 和 `CHAT_BACKEND=fake`。

### 2026-10-17 P1-01：对话模型调用的四个错误类别
`ErrorCategory` 加了四个类别，`chat_error_category(exc)` 把调用时抛出的异常换成类别：

| 类别 | 什么情况 |
|---|---|
| `llm_timeout` | 连接超时（重试用完以后），或者读超时（不重试），或者到了总时限 |
| `llm_error` | 其他网关错误：连不上、4xx、429、5xx |
| `budget_exceeded` | 预算检查不让发，请求没有发出去 |
| `structured_output_failed` | 回答转不成要求的 Pydantic 对象 |

不属于这四类的异常返回 None，免得把程序自己的 bug 当成网关故障。设计 16.8 里「写回答」这一行只说失败时只返回检索到的段，没给类别名。还考虑过只用一个 `llm_error`：调用方就看不出是网关慢了，还是预算用完了；预算用完要换假模型或者等主人加预算，处理办法不一样，所以分开。

### 2026-10-17 P0-04：Document 元数据的具体写法
- title_path 存成字符串，各级标题用「 > 」连起来，比如「Guide > Install」。存成列表的话，LlamaIndex 拼进向量文字时写成「['Guide', 'Install']」，多出括号和引号。代价：标题里本身有「 > 」时，拆回列表会拆错，这种标题很少。ES 里的 title_path 本来就是 text 字段。
- 标题路径里的标题去掉链接地址和图片：「Fix ([#5279](https://...))」写成「Fix (#5279)」。gradio 的更新日志里，一个标题带两三个网址，不去掉的话标题路径能占 100 多个 token，每块能放的正文就少了这么多。
- unit：Markdown 一个文件就是一个单元，写 null。doc_type 按扩展名写 markdown、mdx、notebook。acl_groups 写 ["public"]，是读取器的参数，以后接公司文档时由配置给。images 写空列表：Markdown 里的图片现在留在正文里，设计 5.4 要求的图片文件路径等图片处理做了以后再填。
- language 先写知识库配置的语言（配置是 auto 时写 und），再由 detect_language 按单元改写。
- 元数据里 title_path 排在 source_rel 前面，进提示词的文字先出现标题路径。
- 值为空的字段（比如第一个标题之前那段文字的 title_path）也不进向量和提示词文字，避免出现「title_path: 」这样的空行。
- front matter 的顶层标量值存进 front_matter 字段；列表里是对象的（比如 authors）不存，日期转成字符串。
- source_version、ingest_run_id、content_hash 不放进 Document，写 ES 时再加（设计 5.4）。

### 2026-10-17 P0-04：重排模型的分词器用 tokenizers 库直接读，不用 transformers

### 2026-10-17 P0-04：切块的具体做法
- 按标题切：MarkdownNodeParser 的子类，改了三处。判断哪些行在代码块里，和清洗规则用同一个函数，认 ~~~ 包起来的和缩进的代码块（原版只认行首去掉空格后以 ``` 开头的行）。直接写出 title_path（原版的 header_path 用「/」连接，标题里有「/」就分不清，也不含本节自己的标题）。每节的 id 是 `doc_id#s<序号>`，序号在整页里往下数，原版每节都从 0 开始。
- token 上限：SentenceSplitter 的子类。`max_tokens: 400` 指正文加元数据（title_path 和 source_rel）的 token 数，用重排模型的分词器量，给问题留出约 110 个 token。overlap 设为 0：相邻块的扩展按 doc_id 加 chunk_index 查（设计 7.4），重叠的文字会让 BM25 和去重都多算一次。段落按空行（两个换行）分开。
- 代码块和表格：放得下就整块放进同一块，不从中间切开。一个代码块超过上限时按行切成几段，每段重新加上开头和结尾的 ```，每块仍然是完整的 Markdown。表格超过上限时在两行之间切开，后面的块不重复表头；按行分组并带上表头是 P2 表格步骤的事，质量报告记下了被切开的表格数。
- 评审后修改了代码块的三处。第一，切开的代码块最后一段保留结尾的换行，原来丢了这个换行，紧跟在代码块后面的文字会接在 ``` 后面（「```The loop above」），代码块就合不上了，全部文档里有 13 块这样。第二，每段拼好以后再量一次真实的 token 数，超过上限就对半分：几行拼起来的 token 数可能比各行相加多（真实分词器给结尾的换行算一个 token），不检查的话 SentenceSplitter 会报错。第三，按 CommonMark 判断代码块在哪里结束：结束的 ``` 最多比开头的 ``` 多缩进 3 个空格，缩进更深的 ``` 是代码块里的内容（比如 docstring 里的示例）；原文最后没写结束 ``` 的，whitespace 规则补上，网页显示不变。另外，SentenceSplitter 会去掉每块开头的空格，列表里缩进的 ``` 放在块的开头时，开头的 ``` 没了缩进、结尾的 ``` 还有，就对不上了；现在每块只去掉开头的空行，保留第一行的缩进。质量报告新增「没合上的代码块」块数，全部文档是 0。
- 并入太短的块：少于 50 个 token 的块，以及只有标题的块，并入同一页的下一块；一页的最后一块并入前一块；合并后超过上限就不并。合并后的标题路径：前一块只有标题、而且是下一块的上级标题时，用下一块的路径；其他情况取两条路径相同的开头部分。
- parent_id 写这块所在标题小节的 id。小节本身不写进 ES，按同一个 parent_id 取出所有块，就是这一小节的全文（设计 7.2 说的「大块」）。不按标题切的知识库，parent_id 就是 doc_id。
- 最后一步给整页重新编号 `doc_id#0`、`doc_id#1`……，只保留指向原页面的关系，删掉 LlamaIndex 记的前后块关系，因为它们指向的是重新编号之前的 id。

### 2026-10-17 P0-10：每一路自己的结果放在 RetrievalResult.routes，search_docs 返回时去掉
设计 9.1 说每一路的结果放进元数据，给评测和 trace 用。现在 `RetrievalResult` 加了一个有类型的字段 `routes`：键是路的名字（`bm25`、`vector`），值是这一路融合之前自己的排序列表（`RouteHit`：chunk_id、doc_id、名次、分数）。这个字段和别的字段一样会序列化，评测和 trace 存下来的 JSON 里有它；search_docs（P0-09）在返回给调用方之前用 `model_dump(exclude={"routes"})` 去掉它，调用方拿到的 JSON 不变。评审后改成这样：一开始在字段上设了导出 JSON 时一律不输出，结果别的地方想存下完整结果时也存不下来。比较过三种放法：
- 每个块的 metadata 里记它在两路里的名次：只能记到进了最终列表的块，没进最终列表的块记不到，算不了每一路自己的 Hit 和 nDCG。

### 2026-10-17 P0-10：页面级指标怎么算
- 页面就是 doc_id：设计 5.4 规定 doc_id 由知识库、相对路径和单元（页面文件名或页码）组成，所以按页面标注就是标 doc_id，换切法不用重标。分段级标注（chunk_id）是可选的，没有分段标注的题不进分段级指标，报告里写明算了几题。
- k 按列表里的位置算：Hit@5 看的是最终列表的前 5 段里有没有正确页面。还考虑过先把列表按页面去重、再取前 5 个页面：那样第 12 段才出现的页面也可能算进 Hit@5，数字比调用方实际看到的前 5 段好看。
- 同一页面的几段都在列表里时，只在它第一次出现的位置算一次。不这样做的话，同一页的三段都算相关，nDCG 会超过 1，Recall 也会重复计数。
- nDCG 的理想值最多按 k 条算（设计 14.1）。每一段只分相关（记 1）和不相关（记 0），不分相关程度。
- k 不超过最终列表的长度：最终列表默认 8 段，默认的 k 是 1、3、5、10，其中 10 比 8 大，算出来的「@10」其实就是「@8」，名字会误导人。现在超过的 k 一律改成最终列表的长度（默认变成 1、3、5、8），同时给出警告；两路的列表（默认各 20 条）也按同样的 k 截断。MRR 只看前 max(k) 位，也就是前 8 位，最终列表和两路的几列数字可以直接比。重排延迟曲线也按重排后保留的段数（final_k）同样处理。评审前的写法是两路按前 10 位截断、最终列表实际只有 8 段，两边截断的位置不一样。

### 2026-10-17 P0-10：最终列表按返回的顺序算分，分数相同的先后由检索器决定
评测只看 `chunks` 的顺序，不按分数重新排序。RRF 融合后两段分数相同很常见（比如一段只在 BM25 排第 1、另一段只在向量排第 1），谁在前面由 P0-07 用固定规则决定（比如先比单路名次、再比 chunk_id），不能随机，否则同一配置跑两次，Hit@1 也会有几题不一样。还考虑过对分数相同的段取所有排列的平均值来算指标：能消掉排序的随意性，但 Hit 和 MRR 的计算要复杂很多，而且调用方实际拿到的就是某一种顺序。代价：分数相同的段谁排在前面，会让个别题的 Hit@1 变好或变差；P0-07 的固定规则保证每次跑出来的顺序一样，两次评测之间不会因为这一点出现假的差别。

### 2026-10-17 P0-10：配对置换检验在变化的题少时算精确值，多时按固定种子随机抽
只有得分有变化的题会被翻转正负号。变化的题数 m 满足 2 的 m 次方不超过抽样次数 `iterations`（默认 1 万，也就是 m 不超过 13）时，把所有正负号组合都算一遍，得到精确的 p 值；在只有 0 和 1 两种分数的指标上，这个结果和精确 McNemar 一样（测试里比过 5 题变好、1 题变差都是 0.21875）。变化的题更多时，按 `seed`（默认 0）随机抽 `iterations` 次，p 值按（1 加上和实际一样极端的次数）除以（1 加上抽样次数）算，不会算出 0。还考虑过一律随机抽：只有两三题变化时，换一个种子，随机抽出来的 p 值就会变，而精确值算起来也很快。

### 2026-10-17 P0-10：「能分辨多大的差」按精确 McNemar 推出最少要几题变好
设计 14.4 要求报告开头写明题集能分辨多大的差。报告里每个级别（页面级、分段级）各写一句，按这个级别有标注的题数算：分段级标注是可选的，有分段标注的题可能远少于 65 题。现在的算法：先按没有一道题变差来算，找最少几题变好时精确 McNemar 的 p 值不超过 0.05。65 题时是 6 题变好（p 为 0.03125），也就是 9.2 个百分点；5 题变好时 p 是 0.0625，不够。再算一题变差的情况：要 8 题变好，10.8 个百分点。这和设计里估的 8 到 10 个百分点一致。这是下限：实际评测里常常有题变好、也有题变差，需要的差更大，报告里写了这一句。还考虑过按统计功效算（先估计有多少比例的题会变化，再算有 80% 的把握能看出多大的差）：要先猜一个变化比例，猜的数直接决定结果，现在没有依据。

### 2026-10-17 P0-10：重排延迟曲线的测法
每道题先让检索器（融合和去重，不重排）取一次 30 个候选，再把按融合顺序的前 10、20、30 个分别送去重排。同一道题的三个条数挨着跑，CPU 变热、别的程序抢资源这类慢慢变化的影响对三个条数差不多。只计重排这一次调用的时间；正式计时之前先用题集里的第一题调用一次重排模型，这一次不计时（模型第一次调用通常更慢）。每个条数算重排后前 8 段的页面级指标，再加一行「只按融合顺序、不重排」作对照。真实的测量放在 P0-12。

### 2026-10-17 P0-06：写进每块的三个字段由摄取任务按文档给出，content_hash 按清洗后的整页正文算
- 摄取任务在调用 IngestionPipeline 之前，给 EsVectorStore 一张表：每个 doc_id 对应的 source_version 和 content_hash。EsVectorStore 写块时按块所属的 doc_id 查这张表，再加上这次的 ingest_run_id。三个字段都不经过 Document 元数据，元数据里出现这三个键时直接报错，不发请求（设计 5.4：元数据算进页面哈希）。
- source_version 用连接器给的值，HF 文档是「数据集名@提交 id」。content_hash 是清洗后整页正文的 sha256，同一页的所有块相同，用来查「回答用的是哪一版正文」。
- 还考虑过：content_hash 按每块正文算。P0-07 的按正文去重要先去掉页面路径行再比，用不上存好的哈希；按整页算更符合设计 5.4 的审计用途。

### 2026-10-17 P0-06：旧块用 delete_by_query 删，条件是「doc_id 在待删列表里，ingest_run_id 不是这次」
- 设计 7.4 分两种情况：这次有新块的文档，删掉同 doc_id、ingest_run_id 不是这次的块；这次没有新块的文档（删除或改名），删掉全部块。两种情况用同一个查询条件就够了：没有新块的文档，它所有的块都不是这次写的。每 1000 个 doc_id 发一次请求。
- 删之前先 refresh。不 refresh 的话，delete_by_query 看到的还是被这次覆盖之前的旧版本，会报版本冲突。conflicts 设为 abort，有失败就让这次摄取失败、docstore 不保存，下次摄取再处理一遍。
- 报告里分开写「更新的文档」（只删了多出来的旧块）和「删除的文档」（删了全部块）。

### 2026-10-17 P0-06：收尾的顺序是先删旧块，再把数据代号加 1，最后保存 docstore
- docstore 决定下次摄取删什么，所以 ES 那边全部做完才保存它。如果先保存 docstore、删旧块时进程崩溃，下次摄取会认为这些文档没变，多出来的旧块和已删文档的块就永远留在 ES 里。
- 数据代号加 1 放在保存 docstore 之前：Redis 出错时摄取失败、docstore 不保存，下次摄取会再处理一遍这些改动，再把数据代号加 1。反过来的话，docstore 已经保存，下次摄取认为没有改动，数据代号就一直没加，缓存里一直是旧结果。保存 docstore 失败时，下次摄取会多加一次 1，只是让缓存多失效一次，不会出错。

### 2026-10-17 P0-06：只有这次摄取改动了索引，数据代号才加 1
- 这次有新增、修改或删除的文档时加 1；什么都没变的摄取（比如每天定时跑一次而数据没变）不加，缓存继续有效。失败的摄取不加。
- 任务说明里写的是「每次成功的摄取加 1」。没照这句做的原因：数据代号的作用是让旧缓存不再命中（设计 12.1），索引没变时加 1 只会让缓存白白失效。不会漏加：一次失败的摄取已经写进 ES 的改动，docstore 里还是旧哈希，下次摄取会再当成改动处理一遍，那次一定会加 1。

### 2026-10-17 P0-06：docstore 按索引版本分开存；第一次摄取自动建 v1 和别名
- docstore 文件名用别名当前指向的索引名，比如 `data/docstore/kb_hf_docs_v1.json`，满足设计 7.5「docstore 按索引版本分开存一份」。以后重建到 v2 时，传入 v2 就用另一份 docstore。
- 别名还不存在时，摄取任务调用 P0-02 的 init_kb 建 v1 并把别名指过去；别名指向多个索引时报错。

### 2026-10-17 P0-06：索引记下写入用的向量模型；假向量写进 fake_ 开头的索引
- 第一次写入时，把向量模型（`模型名@维度`，比如 `qwen/text-embedding-v4@1024`）写进索引映射的 `_meta.embed_model`。之后每次摄取先比一下，模型不同就不写，报错说明要建新的索引版本或换前缀。两个模型的向量放在一个索引里没法比较，维度相同时 ES 也不报错（设计 7.5）。
- `--fake-embed` 或 `EMBED_BACKEND=fake` 时，默认的索引前缀是 `fake_`：别名 `fake_kb_hf_docs`、索引 `fake_kb_hf_docs_v1`、docstore `fake_kb_hf_docs_v1.json`、数据代号的键也带 `fake_`。不分开会出两个问题：假向量进了查询用的索引；之后用真向量再跑，docstore 认为文档都没变，不会重新算向量，假向量会一直留着。这是 P0-05 留下的问题「索引要记下用的是真向量还是假向量」的解决办法。

### 2026-10-17 P0-06：映射加 images 和 front_matter 两个字段，已有的索引自动补上
- images 是 keyword，对应设计 5.4 的图片路径。front_matter 是 `{"type": "object", "enabled": false}`：只存在 `_source` 里，不建索引，各页 YAML 头里的键不一样，也不会让映射里的字段越来越多。用 50 篇真实文档第一次运行时，因为清洗规则 front_matter 加的这个键不在映射里，摄取停下了，所以加上。
- 映射是 strict，已经建好的索引（本机的 kb_hf_docs_v1）没有这两个字段。摄取开始时把缺的字段用 put_mapping 加上：只加字段，不改已有的字段，也不影响已有的块。已有字段的定义要改，就要建新的索引版本。
- EsVectorStore 发请求之前检查每块的元数据，有映射里没有的键就报错、一块也不写，错误信息里写明是哪个键。

### 2026-10-17 P0-06：一次摄取只建一个 IngestionPipeline，切块步骤按文档的 pipeline_version 分开处理
- 一个知识库的几种扩展名可以配不同的切块步骤，但 IngestionPipeline 只收一份步骤列表。按扩展名分成几次运行不行：UPSERTS_AND_DELETE 会把这次没传进去的其他扩展名的文档全部当成删除。
- 所以管道里的切块步骤是一个 KbChunker，它调用 P0-04 的 `KbProcessor.chunk`，按每个文档的 pipeline_version 交给对应配置的步骤。后面跟着向量模型。IngestionPipeline 自带的转换缓存关掉（disable_cache），向量缓存用 P0-05 的 L0 缓存。

### 2026-10-17 P0-06：读取失败、防误删检查和锁的具体算法
- 读取失败的比例 = 读取器报错的文档数 ÷ 有处理配置的文档数，超过 `INGEST_MAX_READ_FAILURE_RATIO`（默认 0.05）就停下，什么都不改。没超过时，读取失败的文档用 `docstore.get_document` 取出上次存的 Document 原样传进管道，它的哈希和上次一样，管道当它没变，它的块保留；报告里列出这些文档和错误。从来没读成功过的新文档只记进报告。
- 防误删检查比较的是「这次要传进管道的文档数」（清洗后，加上用旧版本代替的）和「docstore 里的文档数」，少于 `INGEST_MIN_INPUT_RATIO`（默认 0.5）倍就停下，docstore 和 ES 都不动。数据源确实变小时，加 `--allow-mass-delete` 再跑。
- 锁：文件锁，名字是 `ingest:<别名>`，等 `INGEST_LOCK_TIMEOUT_S`（默认 5 秒）拿不到就报错退出，不排队。

### 2026-10-17 P0-06：预算检查按字符数估算；账本每行记下摄取编号
- 用真向量时，调用管道之前先估一次：新增和修改的文档的正文字符数，每篇再加 200（每块还要算标题路径），按一个字符一个 token 算钱，花掉的加上估算超过 28 元就不跑。这和 P0-05 客户端每个请求的估法一样，是上限：英文大约 4 个字符一个 token，命中 L0 缓存的不花钱。P0-05 每个请求发出之前的预算检查照常有效。
- 摄取任务给向量客户端的账本是 RunCostLedger，每行多一个 ingest_run_id，报告里的花费是这次摄取所有账本行的合计。别的进程同时调模型也不会算进这次的花费。

### 2026-10-17 P0-06：保存 docstore 时先写临时文件再改名
- LlamaIndex 的 SimpleKVStore 保存时直接用写模式打开原文件，写到一半崩溃会留下空文件或半个文件，下次摄取读不出来，或者把所有文档都当成新增。现在先写 `<名字>.json.tmp`，写完再用 os.replace 换掉原文件，失败时删掉临时文件。

### 2026-10-17 P0-06 评审后：docstore 记下自己属于哪个索引，索引重建或没有块时不用旧的 docstore
- 问题：执行 `docker compose down -v` 以后，ES 的数据卷被删、索引重建成空的，但 `data/docstore/kb_hf_docs_v1.json` 还在。摄取任务按旧 docstore 判断，所有页面都是「没变」，一块也不写，索引一直是空的（评审时复现过）。
- 现在保存 docstore 时，把 ES 给这个索引分配的 uuid（`index.uuid`，索引重建后会变）写进同一个 JSON 文件。摄取开始时，docstore 里有文档、但记的 uuid 和现在的索引不同，或者索引里一块都没有，就不用这份 docstore，按空的 docstore 处理，所有页面当成新增写一遍。向量从 L0 缓存取，不花钱。报告里写明没用旧 docstore 的原因。
- 本机已有的两份 docstore 是改动之前存的，没有 uuid，各自被当成「属于别的索引」处理了一次，重写 438 块，花费 0 元。
- 还考虑过：只按「索引里没有块」判断。索引重建后已经有人写了一部分块时，这个条件判断不出来；uuid 能区分。

### 2026-10-17 P0-06 评审后：失败的摄取在 ES 里留下的块，由下一次摄取清理
失败的摄取已经写进 ES 的块不会被撤回，docstore 也没保存。原来的做法只靠 LlamaIndex 标记的待删文档来删旧块，有三种情况清理不到：
- 新页面的多余块：失败的那次写了新页面 b 的 3 块，下次 b 只剩 1 块。b 在 docstore 里没有记录，LlamaIndex 把它当新增，不会标记删除，b#1、b#2 一直留着。现在收尾时，这次新增的页面也按「ingest_run_id 不是这次」删一遍。
- 来源已经没有的页面：失败的那次写了新页面 c，下次之前 c 从数据源里消失了。docstore 和数据源都不知道 c，没有人删它。现在摄取开始时用 composite 聚合列出索引里所有的 doc_id，既不在这次输入里、也不在 docstore 里的，收尾时删掉全部块，报告里列在 swept。防误删检查也把这些页面算进去：这次输入少于「docstore 和索引里的页面合起来」的一半，就停下。
- 来源又改回去的页面：失败的那次把 a 写成了新版本，下次之前来源改回了 docstore 里的旧版本。哈希和 docstore 一样，管道当它没变，ES 里留着失败那次的版本。现在摄取在写 ES 之前，把这次要写的页面记进 docstore 旁边的 `<索引名>.dirty.json`，跑成功才删这个文件。下次摄取时，列表里的页面即使哈希没变，也重新处理一遍。

另外两处小改动：bulk 请求按批生成，不再先把全部块的向量复制一份；delete_by_query 返回 timed_out 时也当失败处理，这次摄取失败、docstore 不保存。

### 2026-10-17 P0-11：程序发给 Collector 默认用 OTLP gRPC，HTTP 用设置切换
设置 `otlp_protocol` 有两个值：`grpc`（默认，`otlp_endpoint` 原样使用，`http://` 开头表示不加密）和 `http/protobuf`（在 `otlp_endpoint` 后面加 `/v1/traces` 和 `/v1/metrics`）。集成测试用两种协议各发一条 trace，都能在 Jaeger 里查到；另外起了一个临时的 Collector 容器，两种协议发出的指标都能在它的 Prometheus 接口里看到。默认选 gRPC 的原因：
- P0-02 已经把 `otlp_endpoint` 的默认值定成 Collector 的 gRPC 端口，也测过这条路，换默认值要连带改 P0-02 的设置测试和集成测试。
- `opentelemetry-exporter-otlp` 本来就把 grpcio 装上了，不多装包。
- 一条长连接发所有数据，不用每批数据新建一次 HTTP 请求。

还考虑过默认用 HTTP：OTel 规范建议 SDK 默认用 http/protobuf，公司网络或反向代理只允许 HTTP 通过时也能用。下面两种情况把默认值改成 HTTP：P8 的容器用先启动主进程、再 fork 出多个工作进程的服务器，而 grpcio 在 fork 之后出问题；或者公司网络只允许 HTTP 通过。Collector 发给 Langfuse 只能用 HTTP（设计 15.1），这是 Collector 那一段的配置，和程序用哪种协议无关。

### 2026-10-17 P0-11：辅助函数用自己保存的 tracer 和 meter，不依赖 OTel 的全局对象
`init_observability(settings, service_name)` 返回一个 `Observability` 对象，里面有 tracer、meter、所有指标和业务记录的写入器；`request_span`、`layer_span` 和指标都从当前这个对象取 tracer 和 meter。原因：OTel 一个进程只允许设置一次全局的 TracerProvider 和 MeterProvider，单元测试要反复建立、关闭很多次。全局的 TracerProvider 在第一次建立时设一次（任何模式），设成一个转发用的对象：其他库从它拿到的 tracer 每开一个 span，都交给当时正在用的那套设置。Elasticsearch 客户端这类库只在创建时拿一次 tracer，之后一直用；评审指出，第一版只在第一次 `otlp` 建立时把那时的 provider 设成全局的，关掉再建立以后，这些库的 span 还发给已经关掉的 provider，全部丢失。没有正在用的设置时，这些 span 什么都不记。全局的 MeterProvider 仍然只在第一次 `otlp` 建立时设一次，我们自己的指标不经过它。三种模式：`otlp` 发给 Collector，`memory` 把 span 和指标留在内存里给测试读，`off` 什么都不记，但辅助函数照常能用，请求 id 也照常生成。同一个进程里再调一次 `init_observability` 直接返回已有的对象；`shutdown_observability()` 把缓存的数据发出去，去掉自动打点和成本账本的监听函数，然后才能重新建立。还考虑过每次都用 `trace.get_tracer()` 取全局 tracer：测试里第二次建立的 provider 设不进去，span 会发到上一个已经关掉的 provider。

### 2026-10-17 P0-11：OpenInference 自动打点的内容开关全部写明，向量永远不进 trace
`otel_auto_instrument`（默认开）控制 LlamaIndex 和 LangChain/LangGraph 两个打点包。两个包都用我们自己的 TracerProvider，`separate_trace_from_runtime_context=False`，框架建的 span 的父 span 就是调用它的那个 `layer_span`（单元测试用假的向量模型和假的对话模型验证过，LangGraph 的图也是）。`TraceConfig` 的每一项都在代码里写明，不读 `OPENINFERENCE_*` 环境变量，也不用库的默认值：
- 向量一律隐藏：每段文字 1024 个浮点数，一次批量算向量就有几万个数字，trace 文件很快就满。
- 提示词、回答、检索到的原文跟着 `otel_trace_content`（默认开）。P0 的 trace 只在本机的 Jaeger 和本地文件里，看得到内容方便查问题；以后数据要发到托管服务（LangSmith）时，私有知识库要关掉这一项。
- span 的上限也写明：每个 span 最多 512 个属性（OpenInference 给每个检索到的段记好几个属性，30 段就超过 SDK 默认的 128 个），每个属性值最多 16384 个字符，长原文截断，原文本身在 ES 里，业务记录里有它的 id。

### 2026-10-17 P0-11：字段名和指标名都放在 rag/observe/attributes.py
我们自己的字段用 `rag.` 开头（`rag.kb`、`rag.request_id`、`rag.config_version`、`rag.data_generation`、`rag.route`、`rag.rerank_n`、`rag.error.category` 等）。OTel 规范里已经有的用规范的名字：`service.name`、`service.version`、`error.type`（异常的类名），git 提交用 `vcs.ref.head.revision`，模型用量的指标用 GenAI 规范的 `gen_ai.request.model` 和 `gen_ai.token.type`。指标名也在这个文件里：`rag.requests`、`rag.errors`、`rag.requests.degraded`、`rag.requests.rerank_timeout`、`rag.step.duration`（秒）、`rag.model.tokens`、`rag.model.cost`（元）。有一个单元测试检查 `rag/observe/` 下其他文件里没有直接写这类名字。git 提交优先取设置 `git_commit`（容器里用环境变量 `GIT_COMMIT` 传进来），没有就在启动时跑一次 `git rev-parse HEAD`，取不到写 `unknown`。

### 2026-10-17 P0-11：指标怎么记
- 请求数按知识库、工具名和结果（`ok`、`error`、`cancelled`）分开。任务被取消或进程被中断算 `cancelled`，不算服务出错。
- 错误数按错误类别分开。类别的来源有三个：调用方把结果传给 `RequestScope.set_result()` 时，结果里的标记（degraded、rerank_timeout 等）；`add_error_category()` 手动加的；异常离开 span 时 `classify` 回调给的类别，或者异常自己带的 `error_category` 属性。都没有时记 `unclassified`，表示没归类的异常，多半是代码错误。里层 span 定下的类别会写到异常对象上，外层的请求 span 记同一个类别。degraded 和 rerank_timeout 除了算进错误数，还各有一个计数，设计 15.1 要单独看这两个比例。
- 每一步的耗时用直方图，单位是秒，分桶边界在代码里写明（5 毫秒到 120 秒，共 19 个边界）。SDK 默认的边界是按毫秒数设计的，最大到 10000，用秒记录时大部分桶都用不上。请求本身也按工具名记一次耗时。
- 模型调用次数、token 和花费：`rag.cost` 加了 `add_record_listener`，账本每写一行就调一次监听函数，`init_observability` 注册的监听函数把调用次数（`rag.model.calls`，评审后加上）、输入和输出 token、元数加到计数上，按模型、用途（embedding 或 chat）、档位（ingest、query、online 等）和调用方分开（设计 15.1 要看每个调用方每天的调用次数、token 和花费）。调用方取当前请求的；请求之外的调用，或者在没有复制请求上下文的线程里发出的调用，没有调用方这一项。这样 `rag.cost` 不用依赖 OTel；监听函数出错只写日志，不影响已经发生的模型调用和已经写好的账本行。还考虑过在 P0-05 的向量客户端和 P1-01 的对话模型传输层里各加一段记指标的代码：要改两处，以后新加一种模型调用时，很容易忘了加这段代码。
- 指标里不放请求 id 这类每次都不一样的值，否则 Prometheus 里的序列数会一直涨。

### 2026-10-17 P0-11：Collector 把指标转成 Prometheus 格式，不写文件
`deploy/otel-collector.yaml` 加了 metrics 管道：从 OTLP 接收指标，由 prometheus 导出器在容器的 8889 端口提供 Prometheus 格式，主机端口 127.0.0.1:28889（按 compose 的规则，标准端口加 20000）。本机磁盘只剩大约 16 GB，指标只放在 Collector 的内存里，一个序列 10 分钟没有更新就删掉；P5 起由 Prometheus 定时来取，长期保存也是 Prometheus 的事（设计 15.1）。还考虑过再加一个写文件的导出器：指标每 30 秒一批，文件会一直变大，而 P0 没有人去读它。要让正在运行的 Collector 用上新配置，需要在主目录执行 `docker compose up -d`，重新创建 Collector 和 Jaeger 两个容器。这次没有动正在运行的 Collector：另一位开发者在用这些服务做 P0-06。新配置先用同版本的镜像跑了 `validate`，又在别的端口起了一个临时容器，发了指标、看到了结果，然后删掉了。

### 2026-10-17 P0-11：本地文件都有大小上限
- Collector 的 trace 文件：原来是 50 MB 一个、留 5 个旧文件、7 天，最多占 300 MB。现在是 20 MB 一个、留 3 个旧文件、3 天，最多 80 MB。打开自动打点以后，每次请求的 trace 带着提示词和检索到的原文，文件长得比 P0-02 测试时快很多。

- 业务记录：默认 `data/observe/records/business.jsonl`，20 MB 一个，留 5 个旧文件，最多 120 MB。每次请求一行，大约 3 到 4 KB，20 MB 能放大约 5000 次请求。
- 日志：每个服务名一个文件 `data/observe/logs/<服务名>.jsonl`，同一个服务名的几个进程写同一个文件，10 MB 一个，留 3 个旧文件，每个服务名最多 40 MB。
- `data/observe/` 已经加进 .gitignore。相对路径从仓库根目录算，不从当前工作目录算：MCP 客户端启动服务时的工作目录不一定是仓库。

### 2026-10-17 P0-11：业务记录和日志都用自己写的轮转，几个进程可以写同一个文件
业务记录每写一行都先拿文件锁、打开文件、追加、关闭。文件大小加上这一行超过上限时，先把旧文件依次改名（`business.jsonl` 改成 `.1`，`.1` 改成 `.2`，最老的删掉），再写。这样几个进程可以写同一个文件；Windows 上文件被别的进程打开着就改不了名，每次写完就关文件，能避开这个问题。文件锁最多等 2 秒（评审后加上），等不到就放弃这一行。写失败（磁盘满、路径不对、等锁超时）只写一条警告日志并返回 False，不让请求因为记录写不进去而失败。还考虑过用标准库的 `RotatingFileHandler`：它一直开着文件，两个进程写同一个文件时，Windows 上改名会失败。

日志也用这个写法。第一版的日志用的是标准库的 `RotatingFileHandler`，理由是每个服务写自己的文件。评审指出这个理由不成立：每个用 stdio 方式连接的 MCP 客户端都会自己启动一个服务进程，脚本不传服务名时都用默认的 `rag`，几个进程会写同一个日志文件。让两个进程同时写、每行之间停 5 毫秒，标准库的写法 120 行只留下 78 行，还报了日志错误。还考虑过在文件名里加进程号：每次启动服务都多一组文件，进程退出后没人删，总大小没有上限。

本机每写一行要拿锁、开文件、关文件，大约 6 毫秒（大部分花在建、删锁文件和打开文件上）。业务记录每次请求只写一行，直接在请求里写。日志一次请求可能写好几行，所以请求线程只把这一行格式化成 JSON（trace id 和请求 id 在这个线程的上下文变量里），放进队列；每个进程有一个写日志的线程负责拿锁写文件。队列最多放 1 万行，满了以后新来的行不写，只计数，不让请求等磁盘。`shutdown_observability()` 和进程退出时会先把队列里的行写完。filelock 自己的日志和写日志线程自己产生的日志不写进文件：写它们又会产生新的同类日志。

每行 JSON 有时间（UTC）、级别、logger 名、消息、服务名、trace_id、span_id、请求 id，还有 `extra={...}` 传进来的字段；有异常时加上完整的堆栈。不在请求和 span 里的日志，这三个 id 写 null。标准错误输出默认只显示 WARNING 及以上的短文本；标准输出不写日志，MCP 的 stdio 方式要用标准输出传消息。

### 2026-10-17 P0-11：业务记录的字段
每行一个 JSON 对象：`schema_version`（现在是 1）、时间（UTC）、请求 id、trace id、工具名、调用方、知识库、配置版本（由调用方传，P0-09 用知识库配置的 sha256）、索引版本、数据代号、每一路按名次排的前 10 个段 id 和分数、重排分、阈值判断（阈值、第一名分数、阈值有没有生效、第一名过没过、留下几段、去掉几段）、最终返回的段 id 和分数、结果的标记（错误类别）、每一步耗时（毫秒）、`extra`（以后的轮数、引用核对结果、用户反馈）。`business_record_from_result()` 从 `RetrievalResult` 填好其中能填的字段，trace id 取当前 span 的；重排分和阈值判断由调用方传，P0-07 和 P0-08 写出这两部分以后，P0-09 再把它们传进来。

### 2026-10-17 P0-07：每次查询的调用方信息放在 HybridQuery 里传进 LlamaIndex 检索链
LlamaIndex 的检索器 `_retrieve` 和后处理器只收一个 `QueryBundle`，没有地方放调用方的权限组、过滤条件和截止时间，返回的 `NodeWithScore` 列表也放不下每一路自己的名单。现在 `HybridQuery` 继承 `QueryBundle`，多带四个字段：`acl_groups`、`filters`、`deadline`（往里传），`trace`（往外带：每一路的名单、失败的路和原因、索引版本、候选数、去重删掉了哪些块、各步耗时）。每次请求新建一个，检索器对象本身不存请求的状态，多个线程可以共用。`EsHybridRetriever` 收到普通的 `QueryBundle` 或字符串直接报错，不会在没有权限过滤的情况下查询。还考虑过：
- 每次请求新建一个检索器，把这些值放进构造参数：能用，但 P0-08 的后处理器同样需要截止时间，还得另想办法传。
- 把最近一次的结果存在检索器的属性上：两个请求同时进来会互相覆盖。
- 每一路的名次只写进每个块的 metadata：没进融合结果的块记不下来，算不了每一路自己的指标（P0-10 已经因为这个原因选了 `RetrievalResult.routes`）。

### 2026-10-17 P0-07：调用方能用的过滤字段，和服务端追加的两个条件
过滤条件是一个列表，BM25 放在 `bool.filter`，向量放在 `knn.filter`，两路完全一样。列表的前两项总是「kb 等于这个知识库」和「acl_groups 包含调用方的任一权限组」，由服务端按请求的知识库和调用方身份加上。调用方的 `filters` 只认三个键：`doc_type`、`language`（一个值或一个列表）和 `source_rel_prefix`（一个路径前缀），对应设计 16.1 的白名单。其他键一律报 `invalid_filter`，包括 `acl_groups` 和 `kb`，所以调用方既不能换掉权限条件，也不能去掉它。权限组为空时直接报错，不会变成「没有权限条件」。值必须是非空字符串或非空字符串列表，传一个字典进来（想夹带查询语法）也报错。

### 2026-10-17 P0-07：RRF 分数相同时的排序规则
按 P0-10 的决定，分数相同的块由检索器用固定规则排：先比融合分数，分数相同再比「在任一路里最好的名次」，还相同就按 chunk_id 字母顺序。融合分数用分数（`fractions.Fraction`）精确计算再比较，返回时才转成浮点数。原因：两段在两路里的名次正好对调（一段是第 2 和第 3，另一段是第 3 和第 2）时，分数本来相等，但浮点数换个顺序相加，最后一位可能不一样，同一配置两次的顺序就可能不同。每次查询最多 40 个候选，精确计算的耗时可以不计（实测融合一步 1.5 毫秒）。还考虑过分数相同时固定让 BM25 那一路的块排前面：要先说清哪一路更可信，现在没有依据。

### 2026-10-17 P0-07：一路失败怎么判断；部分结果不用
`_msearch` 的响应里每个搜索各有一个结果。一个结果带 `error`（比如向量维数不对返回 400），或者带 `timed_out: true`，这一路就算失败：不进融合，`failed_routes` 记下原因，结果标 `degraded`。超时的那一路即使带着部分命中也不用：部分结果是按 ES 内部的处理进度截断的，排序不可靠，混进融合以后也看不出它不完整。两路都失败时抛 `RetrievalError`：所有失败都是超时，类别是新加的 `retrieval_timeout`，否则是 `retrieval_failed`；整个请求连不上、HTTP 超时或返回非 2xx，也按这两个类别报。问题向量算失败（网关出错、预算用完、超时）只影响向量这一路：只把 BM25 的查询发给 ES，标 `degraded`。

### 2026-10-17 P0-07：截止时间怎么往下传
请求开始时把总时限变成一个 `Deadline`（某个单调时钟读数）往下传。没传时用新加的设置 `search_deadline_ms`，默认 10 秒。
- 先查 L0 缓存（Redis），最多等剩下时间的一半；命中就直接用，不受下一条的限制。没命中再在线程里调网关，最多等到截止前「`search_es_reserve_ms`（默认 200 毫秒）和总时限的 `search_es_reserve_ratio`（默认 20%）里较小的那个」，这段时间留给 ES 查询；等不到就只查 BM25，标 `degraded`。没等完的那次网关调用在后台继续，结果写进 L0 缓存，它本身受查询配置的 7 秒总时限限制（P0-05）。评审前留给 ES 的是固定的 1 秒，见下面「P0-07 评审后」一条。
- `_msearch` 的 HTTP 超时是剩下的时间；里面每个搜索另设 ES 的 `timeout`，比 HTTP 超时早 `search_es_margin_ms`（默认 200 毫秒，最多占剩下时间的一半，见「P0-07 第二轮评审后」）。这样慢的一路会先以 `timed_out` 返回，另一路照常用；如果两个时间一样，HTTP 请求先被断开，两路就一起失败了。
- 查询用的 ES 客户端不重试（`max_retries=0`），一次失败就按上一条处理，不在截止时间里再试一次。

还考虑过不放线程、直接同步调用向量接口：调用方给的时限比查询配置的 7 秒短时（比如 2 秒），一次网关故障就会让整次查询超出调用方的时限。也考虑过先单独发 BM25、等向量算好再发 kNN：要两次网络往返，和设计 9.1「两个查询放进一次 _msearch」不符。代价：后台线程最多 `embed_max_concurrency` 个（默认 4），网关一直很慢时线程都被占着，新的问题等不到线程，就都只用 BM25，直到网关恢复。实测 50 篇文档的索引上，网关算一个问题向量的中位数约 810 毫秒，ES 一次 `_msearch` 约 17 毫秒。

### 2026-10-17 P0-07：按正文去重比较什么
设计 9.3 说「去掉页面路径行后按正文比」，那是前期项目的块文字第一行带页面路径。这个平台的块正文（ES 的 `content` 字段）本来就只有正文，标题路径和页面路径是单独的字段（P0-06），所以 `TextDedupe` 比较的是正文。另外，正文里和这个块自己的 `source_rel` 或 `source_url` 完全相同的整行也去掉再比，以后如果给正文前面加上路径行，去重照样有效；句子里提到的路径不去掉。比较之前做 Unicode NFKC 归一化、转小写、把连续空白换成一个空格。保留融合排名最靠前的那一块，删掉的块 id 和保留的块 id 记进 trace。去重在截到 top_k 之前做，重复的块不占最终列表的位置；不补查（9.3）。还考虑过比较正文的哈希、不做归一化：同一段文字在两个页面里空格、换行或大小写稍有不同（转换工具不同常见这种情况），就去不掉。

### 2026-10-17 P0-07：BM25 用 best_fields，标题权重 2；num_candidates 100
BM25 一路用 `multi_match`，字段是 `content` 和 `title_path^2`，`type` 写明 `best_fields`（取两个字段里得分高的那个）。没用 `most_fields`（两个字段的分相加），我的推断：标题路径很短，又和同一页的很多块相同，相加以后标题命中的块会整页一起排到前面，正文真正相关的块反而排到后面。权重 2、`num_candidates` 100、`rrf_k` 60 都写进了知识库配置（`RetrievalConfig`，`kb/public/hf_docs.yaml` 里也写明了），等全量数据（P0-12）建好后在题集上调。`num_candidates` 小于每路条数时配置直接报错（ES 要求 num_candidates 不小于 k），上限 10000 是 ES 的限制。

### 2026-10-17 P0-07：建检索链时检查索引用的向量模型
`make_hybrid_search` 先找出别名指向的索引，比较索引映射里记的 `_meta.embed_model`（P0-06 写入）和查询要用的向量模型（同样按 `模型名@维数` 算）。不一致就报 `IndexEmbedModelError`，不建检索链。原因：用真向量去查假向量建的索引（或者反过来），维数相同时 ES 不报错，向量那一路只会返回没有意义的结果，从评测数字上也很难看出原因。`index_prefix="fake_"` 时查 `fake_kb_hf_docs`，配合 `EMBED_BACKEND=fake`。

### 2026-10-17 P0-07：返回给调用方的每一段带哪些元数据
`Chunk` 已有的字段（chunk_id、doc_id、正文、标题路径按「 > 」拆成列表、source_rel、source_url、source_version、疑似指令标记）之外，`Chunk.metadata` 放 `route_ranks` 和 `route_scores`（这一段在每一路里的名次和那一路自己的分数）、`doc_type`、`language`、`chunk_index`、`parent_id`、`images`。不读也不返回 `acl_groups`：调用方不需要知道一段内容还对哪些权限组开放。向量本身不读（索引设置了 `exclude_source_vectors`，查询里也只列出需要的字段）。`score` 是融合分数。

### 2026-10-17 P0-07 评审后：留给 ES 的时间按总时限的比例算，缓存命中先用；另外五处修正
- 留给 ES 的时间：评审前固定留 1 秒，调用方传 1 秒或更短的总时限时，等问题向量的时间是 0，向量那一路每次都不查，连 L0 缓存里已有的向量也不用，而一次 `_msearch` 实际只要 17 毫秒左右。现在留「200 毫秒和总时限的 20% 里较小的那个」（`search_es_reserve_ms`、`search_es_reserve_ratio`，都在服务设置里）：总时限 300 毫秒时留 60 毫秒，1 秒以上时留 200 毫秒。缓存查找放在这一步之前，最多等剩下时间的一半，命中就用；查缓存用单独的线程，网关线程全部在等一个不响应的网关时，缓存照样能查。代价：没命中时要多查一次 Redis（网关客户端自己还会再查一遍），约 1 毫秒。还考虑过只把固定值改小（比如 200 毫秒）：总时限 200 毫秒以下时还是一样的问题，按比例算没有这个下限。
- 权限组传成一个字符串（`"grp"`）时，评审前会被拆成 g、r、p 三个组。现在 `build_es_filter` 和 `HybridSearch` 都直接报 `TypeError`，要求传列表或元组。
- 数据代号评审前在检索完成后同步读 Redis，Redis 不响应时要等到它的连接超时（默认 5 秒），可能超出调用方的时限。现在和检索同时在另一个线程里读，最多等到截止时间，读不到就记 0，检索结果照常返回。
- 两路都没有命中时，评审前 `index_version` 是空的（索引名是从命中里读的）。现在这种情况下用一次 `get_alias` 查出别名指向的索引，时限是剩下的时间，查不到就留空，不让这次检索失败。
- 过滤条件的键不是字符串（比如数字）时，评审前在排序时抛出 Python 的 `TypeError`；现在报 `invalid_filter`。
- 每个搜索单独设的 ES `timeout` 对 kNN 是否生效没有验证：在本机 438 块的索引上把 timeout 设成 1 纳秒，BM25 和 kNN 都正常返回、`timed_out` 都是 false（索引太小，ES 在第一次检查超时之前就查完了），所以测不出来。等 P0-12 全量数据建好后再测；在那之前，kNN 很慢时可能要等到整个 HTTP 请求超时，两路一起失败。
- `Chunk.score` 的说明里写明：混合检索返回的是 RRF 融合分数，每一路自己的名次和分数在 `metadata` 里。

### 2026-10-17 P0-07 第二轮评审后：每个搜索的 ES 超时比 HTTP 超时提前多少，最多是剩下时间的一半
第一轮评审后，留给 ES 的时间是「200 毫秒和总时限的 20% 里较小的那个」，而每个搜索的 ES `timeout` 比 HTTP 超时早固定的 200 毫秒。两者放在一起有问题：总时限 800 毫秒时只留 160 毫秒，缓存没命中、网关又一直不回时，等完向量只剩约 160 毫秒，每个搜索的 ES `timeout` 算出来是 160 减 200，按下限取 1 毫秒，连 BM25 也会超时，结果是 `retrieval_timeout`，而不是只用 BM25 的 `degraded` 结果。现在提前的时间取「200 毫秒和剩下时间的一半里较小的那个」：剩 160 毫秒时提前 80 毫秒，每个搜索有 80 毫秒（一次 `_msearch` 实测约 17 毫秒）；剩 3 秒时仍提前 200 毫秒。单元测试用一个按 ES 规则回答的假客户端（搜索要 17 毫秒，`timeout` 比这短就返回 `timed_out`）复现了这个问题：改之前抛 `retrieval_timeout`，改之后返回 BM25 的结果并标 `degraded`。

还考虑过让留给 ES 的时间至少是「提前的 200 毫秒再加 100 毫秒」（300 毫秒）：总时限 300 毫秒以下时就不会再调网关，第一轮评审修掉的「短时限下向量那一路总是不查」又会出现。按剩下时间的一半限制提前的时间，对任何时限都成立。

### 2026-10-17 P1-02：写回答的代码放在新的 rag.answer 包里

### 2026-10-17 P1-02：上下文预算按估算的 token 数算
`build_context` 默认用 `estimate_tokens` 数 token：中日韩字符每个算 1 个，其余字符每 3 个算 1 个；数的是渲染好的整个片段（编号、分隔符、标题路径、来源和正文）。知识库配置 `answer.context_tokens` 默认 4000（设计 10.3）。原因：网关上的 deepseek-v4-flash 没有能在本机加载的分词器；英文实际大约 4 个字符一个 token，按 3 个算会多算，片段只会比预算少，不会超出。`llm` 测试那一次，估算的提示词是 1868 个 token，网关记的是 1351 个，估算多了大约 38%。还考虑过：
- 用重排模型 bge-reranker-base 的分词器（本机有缓存）：词表和 DeepSeek 不同，数出来同样是近似值，单元测试还要依赖本机的 HF 缓存。
- 用 tiktoken：要另外下载词表文件，词表也不是 DeepSeek 的。

调用方可以传 `count_tokens` 换掉估算。P1-04 跑完 65 题以后，如果估算普遍多出三成以上，而回答又缺片段，就把「每 3 个字符」改成「每 4 个字符」。

### 2026-10-17 P1-02：每个子问题先平均分一份预算，剩下的按重排分给别的子问题
`build_context` 接收每个子问题一份排好序的块列表：现在一个问题只传一份，P3 拆成子问题以后传多份。做法：
1. 按块 id 去重。同一块出现几次时，留名次最靠前的那一次；名次一样时留排在前面的子问题的。
2. 每个子问题分到「总预算除以子问题个数」那么多 token，按名次从前往后放，放不下就停。
3. 剩下的预算给所有还没放进去的块，按重排分从高到低（没有分数时按名次）一块块试，放不下的跳过，接着试下一块。
4. 编号按名次轮流排：先是每个子问题的第 1 名，再是每个子问题的第 2 名，最相关的在最前面。

原因：设计 10.3，只按分数从高到低放，第一个子问题的块会占满预算，两跳题的第二跳放不进来。第 2 步遇到放不下的块就停，是为了一个子问题自己的那份里，不会出现排在后面的块放进去了、排在前面的块没放进去；第 3 步跳过放不下的块，是为了把剩下的预算用完。还考虑过不分份额、所有子问题的块直接轮流放：几个子问题的块大小差得多时，块大的子问题占掉大部分预算。

### 2026-10-17 P1-02：片段用固定的分隔符包起来，系统消息固定不变
每个片段渲染成：一行 `[n]`；然后 `<doc_fragment n="n" untrusted="true">`；里面是知识库白名单里的元数据（`title_path: A > B`、`source_rel: ...`，每个一行）、一个空行、正文；最后是 `</doc_fragment>`。命中疑似指令检测的块，开头的标签里多一个 `suspicious_instruction="true"`。正文和元数据里出现的 `<doc_fragment`、`</doc_fragment`（不分大小写，中间可以有空格），都把 `<` 换成 `&lt;`，这样块里的文字不能提前结束自己的片段、再伪造一个新片段；元数据里的换行换成空格。系统消息每种语言一个固定的字符串，片段和问题只放进用户消息，片段在前、问题在后，问题里的分隔符同样转义。单元测试检查：放进一段带注入文字的块以后，系统消息和没有这块时完全相同，注入文字在第二个片段的两个标签之间。

原因：设计 11.3 的第一条做法。标签名用 `doc_fragment`，不用 `fragment`：HF 文档的 mdx 页面里有 React 的 `<Fragment>`，不分大小写转义时会改到正文里的代码。还考虑过每次请求随机生成一个分隔符：伪造不了，但每次的提示词都不一样，单元测试没法比较；转义已经能防止伪造。

### 2026-10-17 P1-02：回答语言按问题里的汉字数和英文单词数判断
`detect_question_language` 先去掉代码块、行内代码和网址，再数汉字和英文单词；汉字数除以 1.5 不少于英文单词数时用中文，否则用英文。只数普通单词（`Trainer`、`batch`、全大写的缩写），`device_map=auto`、`from_pretrained`、`LoRA` 这类标识符不数。知识库配置 `answer.language` 设成 `zh` 或 `en` 时不判断，直接用设的语言（设计 8.4）。别的语言的问题用英文提示词。

原因：「`AutoModelForCausalLM.from_pretrained` 的 device_map=auto 和 torch_dtype 怎么配」这样的问题只有 5 个汉字，参数名按下划线和等号分成单词以后却有 5 个英文词，只比较字数和词数的话，这题会被当成英文问题。还考虑过直接用摄取时的 `rag.ingest.language.detect_language`：它把标识符按下划线分成英文单词来数，上面这题会被当成英文问题；导入它还会把 `rag.ingest` 的读取器和 LlamaIndex 处理步骤一起导入。

### 2026-10-17 P1-02：流式接口逐个给出事件，不流式的调用也用流式调模型
`stream_answer` 是一个异步生成器，依次给出 `AnswerDelta`（模型生成的一段文字，带 [1] 这类编号）、重试时的 `AnswerRetry`（之前的文字作废）、最后一个 `AnswerDone`（解析和核对以后的 `Answer`），对应设计 16.9 的 token 和 answer 两种事件。`generate_answer` 把同一个流读完，只返回最后的回答。调模型一律用 `astream`：P1-01 的 online 档位读超时 10 秒，不流式时这 10 秒限制的是整个回答的生成时间，流式时只限制前后两段数据之间的间隔（P1-01 记下的遗留问题）。`llm` 测试那一次回答用了 5.45 秒，分 10 段到达。还考虑过：
- 流式和不流式各写一套调用和解析：两套代码要一起维护，行为容易不一致。
- 生成器只给出字符串，最后的回答放在对象的一个属性上：调用方要另外判断什么时候重试、什么时候结束，SSE 那一层还要再包一次。

### 2026-10-17 P1-02：怎么解析 [n]，什么算解析失败
- 认的写法：`[1]`、`【1】`、`［1］`、`[1,2]`、`[1，2]`、`[1、2]`、`[1][2]`、`[1-3]`（最多展开 50 个）、`[source 1]`、`[片段1]`。编号写在句号后面，也算前一句的。
- 句子在哪里结束：`。！？` 一律算；`.!?` 只有后面是空格、换行、文字结尾或编号时才算，所以 `1.5`、`config.json` 不算，`e.g.`、`i.e.`、`vs.` 后面也不算；换行算。行内代码和代码块整体当作正文，里面的 `x[0]` 不当编号。行首的列表符号和 `#` 先去掉。
- 那句固定的话：去掉编号、空格、引号、星号和句号，不分大小写比较，中英文两句都认。回答里既有正常的句子、又有这句话时，去掉这句话，其余照常处理。
- 引用核对第一层（设计 11.2）：不在 1 到片段数之间的编号去掉，记进 `citation_check.removed_markers`；一个有效编号都没有的句子记为没有依据（`unsupported_sentences`）。
- 一个有效编号都没有（编号全都超出范围也算），又不是那句固定的话，就算解析失败。这时把第一次的回答作为模型的回复放回消息里，再加一条提醒格式的用户消息，重新调一次（`answer.parse_retries`，默认 1）；还是失败，就标 `answer_parse_failed`，只返回片段，`citation_check` 记最后一次的数字。

### 2026-10-17 P1-02：没找到、解析失败、模型出错时 Answer 怎么填
- 模型输出那句固定的话：`found=false`，`status=not_found`，`sentences` 只有一句，是回答语言的那句固定的话（问题是中文、模型写了英文的那句，也返回中文的那句），这句不算没有依据。
- 一个片段都没有（检索没找到，或者预算太小、一段都放不下）：不调模型，按上一条返回，`parse_attempts` 是 0。
- 解析失败，或者模型出错（`llm_timeout`、`llm_error`、`budget_exceeded`，P1-01 的传输层已经重试过）：`found=false`，`status=not_found`，没有句子，`chunks` 是片段，`error_categories` 里有 `answer_parse_failed`，或者新加的 `generation_error` 字段里的类别（设计 16.8「失败只返回检索到的段」）。其他异常是代码错误，照常抛出。
- `Answer.chunks` 永远是按编号排好的片段，编号 n 对应 `chunks[n - 1]`。

`status` 用 `not_found`，是因为设计 16.1 只定了三个状态，加一个 `failed` 要改对外的返回结构；调用方先看 `error_categories`，有类别就说明不是知识库里没有答案。还考虑过 `status=answered`、回答文字为空：调用方会把空回答当成正常回答显示出来。

`generate` 这一步的 span 上记：片段数、估算的 token 数、预算、因为预算去掉的块数、重复的块数、疑似指令的片段数、回答语言、found、句子数、没有依据的句子数、去掉的编号数、调模型的次数、是否解析失败，以及这次回答写进成本账本的行数、元数和 token（`gen_ai.usage.input_tokens`，`gen_ai.usage.output_tokens` 含推理 token）。花费的取法：`rag.answer` 给成本账本注册一个监听函数（每个进程一次）；每次回答开始时在上下文变量里放一个空列表，账本每写一行，监听函数就把这一行加进当前上下文的列表，同时进行的几个回答各记各的。还考虑过给账本的每一行加上请求 id（P0-11 记下的遗留问题）：要改账本格式，还要改 P0-05 和 P1-01 两处写账本的代码，这次用不着。

### 2026-10-17 P1-02 评审后：五处修正
- 代码里的方括号不再当成引用编号。第一版把 `logits[1]`、缩进的 `a[1] = 3`、`torch.Size([1, 2])` 里的方括号读成引用，从句子里删掉了。现在：英文方括号紧跟在英文字母、数字、下划线、括号、花括号或等号后面时，算代码，原样留在句子里；行首有 4 个空格或制表符的行整行当代码。仍然算编号的情况：全角括号（`［3］`、`【3】`），紧跟在汉字或另一个编号后面（`中文[1][2]`），后面紧跟中文标点（`窗口是 127[2]。`，中文回答常这样写）。代价：英文回答写成 `attention[1].`（编号前没有空格）时，这个编号会被当成代码，这句话算没有依据；`llm` 测试那一次模型在编号前加了空格。还考虑过只按「前面是不是字母」判断：`127[2]。` 这种中文回答里的编号都会被当成代码，这些句子都变成没有依据。
- 只说「没找到」的回答不再重试。第一版只认那句固定的话，模型写成「I'm sorry. The documentation does not contain the answer.」时，「I'm sorry.」没有编号，被当成解析失败，重试以后标 `answer_parse_failed`。现在先认出说片段里没有答案的句子（英文是 documentation、fragments、context 开头，后面接 does not contain、mention、include 等；中文是手册、文档、片段、资料开头，后面接没有找到、没有提到等），其余句子一个编号都没有时，按没找到处理（`found=false`），不重试。其余句子有编号时，照旧去掉这句、保留其余。
- 片段里伪造的编号行和变形的分隔符也转义。一块正文里如果有一行只写 `[2]`，模型可能以为第 2 个片段从这里开始；现在正文和问题里行首的 `[n]`、`【n】`、`［n］` 前面加一个反斜杠。分隔符的转义也认全角的 `＜`、`／` 和全角字母、小号的 `﹤`，以及夹在标签名里的零宽字符（零宽空格、零宽连接符、BOM 等）；只把开头的 `<` 换成 `&lt;`，其余文字不动。还考虑过把编号行挪进分隔符里面：设计 10.3 写的是「每段前面带编号」，伪造的编号行在片段里面也一样能混淆，转义行首编号两种情况都能处理。
- `generate` 这一步的 span 和花费记录只在调模型的时候生效。第一版在整个流式过程中都让这个 span 当前有效、都在收集成本账本的行，调用方在两段文字之间自己做的事（比如自己调一次模型）也算进了这次回答，调用方建的 span 也挂到了 `generate` 下面。现在 `layer_span` 加了 `activate=False`：span 开始时不设成当前 span；每次从模型的流里取下一段时，用新加的 `activate_span` 让它当前有效、同时收集账本行，取完马上还原，再把文字交给调用方。模型的流和中间的生成器都用 `contextlib.aclosing` 包起来，调用方提前关掉回答的流时，模型的流跟着关闭，span 记为取消。剩下的问题：提前关闭时，传输层估算的那一行账本是事件循环在关闭之后才写的，不算进这个 span。
- 重试时的提醒按情况说。回答里的编号都超出范围（比如只有 3 个片段却写了 [7]）时，提醒里写明「[7] 没有对应的片段，片段编号是 [1] 到 [3]」，不再说「没有标任何编号」。

### 2026-10-17 P1-02 第二轮评审后：带编号的「没有提到」句子算回答
第一轮的修正把「The documentation does not mention a GPU requirement [1].」「文档中没有提到超时参数[2]。」这类句子也当成「没找到」，回答的结果是 `found=false`，排在前面的这类句子还会被删掉。可是这类句子标了编号，说的是片段 1 里确实没有这项要求，这是有依据的回答。现在只有一个编号都没标的句子才可能算「没找到」的说法；标了编号的照常当回答的一句。另外，英文提示词的第 2 条和重试提醒都要求「方括号前面留一个空格」：方括号紧跟在英文字母后面时会被当成代码（见上一条）。
